# v0.19 设计：检索与发现层（RAG 接层）——「问我的学习库」＋ 建议制关联发现

> 状态：**草案 · 待批准**（2026-09-03 起草；批准后入排期与需求池登记）
> 依据：用户 2026-09-03 方向裁决「方案三：**派生索引＋双读路径＋人工裁决闭环**」（= 加一层能力 B ＋ 换引擎 C 的良性内核；整体重定位 A / 引擎替换 C 否决）；用户追问「能否 B+C / 更优方案」后定案
> 关联：[ADR-029](../../adr/ADR-029-rag-retrieval-discovery-layer.md)（随本设计，提议态）· [ADR-010](../../adr/ADR-010-gap-filling-ai.md)（AI 为增强层·本地兜底铁律）· [ADR-024](../../adr/ADR-024-knowledge-system-layer.md)（体系只引用不收纳·AI 只建议不生成）· [ADR-028](../../adr/ADR-028-ai-goal-planner.md)（建议制确认落库/预算硬顶/双闸门范式）· [v0.16.0 AI 对话](../../versions/v0.16.0.md)（ai_chat/content_gate/轨迹基建）· REQ-024（AI 多轮问答）· REQ-231（聊天上下文注入 L3 全库检索）· v0.13.4 交叉点派生提示默认关

## 一、一句话

在既有闭环（采集提取 → 笔记/闪卡 → 知识体系 → 目标）旁新增**检索与发现层**：本地全库混合检索（FTS5 词汇 + 本地 embedding 语义）作为**派生索引**（可整体重建，永不当系统记录），向上开两条读路径——**A 问我的学习库**（AI 对话 L3 全库问答，逐条引用回跳笔记，AI 默认关）与 **B 检索建议**（概念/体系的"相关证据"候选与跨体系相似提示，建议制·人工确认后经既有引用通道落库，默认关）；无 embedding 模型时自动降级纯 FTS5，无 AI 时降级命中片段列表——层层有本地兜底。

## 二、用户裁决记录（2026-09-03）

| 议题 | 裁决 |
|---|---|

## 三、分层定位与术语（沿用既有 L1–L4 口径）

既有能力分层（[无云端 AI 提取极限](../../Foresight/brainstorming-no-cloud-ai-extraction-limit.md)）：L1 信号 / L2 文本（ASR/OCR）/ L3 结构（章节/术语/检索）/ L4 语义（总结/问答，LLM 专属）。

**代码现状核查（2026-09-03）**：笔记/会话/OCR 图内检索全部为 `LIKE ... ESCAPE` 参数绑定（`db_notes.rs::search_notes`/`db_sessions.rs`/`db_ocr_search.rs`）；**FTS5 全库未实装**；`/goal` 的"L3 FTS top-K"实为**最近笔记标题占位**（`commands_goals_plan.rs::goal_chat_context` + `db_goals.rs` 注释）；`budget_allocator::pack_fragments` 已为"多片段检索打包（随 REQ-024 检索增强启用）"预留 dead_code。→ REQ-024/REQ-231 的检索欠账真实存在，本设计即偿还。

本设计把既有 L3 细化为两层：

| 层 | 名称 | 内容 | 引擎 |
|---|---|---|---|
| L3 | 结构/检索层（升级） | 全库词汇检索（FTS5）+ 语义检索（embedding，可空）→ RRF 融合 | kb 混合检索 |
| L3.5 | **检索与发现层（本设计新增）** | 派生索引管理与生命周期；问答读路径 A；建议制发现读路径 B | kb 索引 + 双读路径 |
| L4 | 语义层 | 问答生成（仅读路径 A 需要，LLM 专属） | ai_platform（默认关） |

## 四、架构总览与三条铁律

```
┌───────────────────────────────────────────────┐
│ 结构化事实源（唯一真相，零改动）                   │
│ notes / fragments / note_groups / sessions /   │
│ knowledge_* / flashcards / goals …             │
└───────────────────┬───────────────────────────┘
                    │ 派生（钩子 + 全量重建，永不当记录）
                    ▼
┌───────────────────────────────────────────────┐
│ 检索与发现层（kb_* 表，纯新增，可整体重建）         │
│ kb_chunks（节级文本）＋ FTS5 影子表 ＋ embedding   │
│ （BLOB 可空）＋ kb_meta（模型版本/统计）            │
└───────┬───────────────────────────┬───────────┘
        │ 读路径 A（问答）            │ 读路径 B（发现）
        ▼                            ▼
   ChatPage「学习库问答」         体系页/概念详情「检索建议」
   命中片段列表（恒可用·本地）      证据候选/相似概念候选
   ＋ 云端生成（默认关，引用溯源）   人工确认 → link_knowledge_target
   无 AI → 仅命中列表               （交叉点默认关延续）
```

**铁律 1 · 单一事实源**：`notes`/`fragments` 等既有表是唯一真相；检索层只读事实源、永不反向写回；chunk 文本为**派生副本**。
**铁律 2 · 派生可重建**：`kb_*` 表可由事实源全量重建（`reindex_all`）；版本/损坏/模型更换 → 重建即愈；向量索引错误绝不损坏事实源。
**铁律 3 · 人工裁决闸门**：任何向量输出（B 路径建议）**不得直接写入结构层**——经确认后仅走既有引用通道（`link_knowledge_target`，target_type 白名单 note/fragment 已有）；延续"AI 只建议不生成"（ADR-024/028）。

## 五、索引层设计

### 5.1 chunk 粒度与来源

- **chunk 源 = 净化后文本**：`notes.content`（会话转笔记已在入库前净化：去 UI 噪音/重复/低置信；含 `[MM:SS]` 时间锚点文本）＋ `fragments.text`（纯文本碎片）。**原始转写/OCR 原料不入索引**（噪声毁检索质量；会话/时间轴检索属 REQ-023 远期）。
- **节级切块**（heading-aware）：按 markdown 标题行（`#`/`##`…）切；无标题长文按段落聚合至 ≤ 800 字符硬切（embedding 窗安全余量；节级粒度为"笔记 5~15 块/篇"，控制向量总量）；chunk 记录 `(heading, char_start, char_end)` 以便命中跳转定位。
- 引用溯源天然成立：每 chunk 携带 `note_id/fragment_id` → 组名 join → 笔记标题/节标题 + snippet 即引用卡片。

### 5.2 表与迁移（纯新增三表 + 两处补列，既有表 DDL 零改动）

```sql
CREATE TABLE IF NOT EXISTS kb_chunks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source_kind TEXT NOT NULL CHECK (source_kind IN ('note','fragment')),
    note_id INTEGER REFERENCES notes(id) ON DELETE CASCADE,      -- source_kind='note'
    fragment_id INTEGER REFERENCES fragments(id) ON DELETE CASCADE, -- source_kind='fragment'
    ord INTEGER NOT NULL,                       -- 节内顺序
    heading TEXT,                               -- 所属节标题（无标题 NULL）
    char_start INTEGER NOT NULL, char_end INTEGER NOT NULL,
    text TEXT NOT NULL,
    embedding BLOB,                             -- f32 向量（长度=kb_meta.dim）；无引擎 NULL
    CHECK ((source_kind='note'     AND note_id IS NOT NULL AND fragment_id IS NULL)
        OR (source_kind='fragment' AND fragment_id IS NOT NULL AND note_id IS NULL))
);
-- 多态源用双可空 FK 列（flashcards.note_id/fragment_id 同款先例）；主清理路径 =
-- 删除事务内显式先清（见 5.3），FK CASCADE 仅兜底（级联不负责影子表，勿依赖）
CREATE INDEX IF NOT EXISTS idx_kb_chunks_source ON kb_chunks(source_kind, note_id, fragment_id);
CREATE VIRTUAL TABLE IF NOT EXISTS kb_fts USING fts5(
    text, chunk_id UNINDEXED,
    tokenize = 'unicode61 remove_diacritics 2'
);  -- 词法影子表；BM25 对中文的切词口径 spike 校准
CREATE TABLE IF NOT EXISTS kb_meta (
    key TEXT PRIMARY KEY, value TEXT NOT NULL
);  -- embedding_model/dim/format、index_version、stats
```

- FTS5 使能核查：`rusqlite` bundled 构建需确认带 FTS5（必要时补 `fts5` feature/编译宏）——纯源码编译，无预编译下载，**不受本机 TLS 拦截影响**（AGENTS.md §9 约束内）。
- 迁移合规：db-migration 模板；幂等 `CREATE TABLE IF NOT EXISTS` + `ensure_column` 惯例。**既有表零 DDL 改动，仅两处 ensure_column 补列**：`chat_sessions.retrieval`（§7.1）、`chat_messages.meta_json`（v0.16 `trajectory_json` 补列同款先例）。
- **影子表同步纪律**：`kb_chunks`/`kb_fts` 的一切写入收敛于 kb_index 模块、同事务双写（不依赖 SQLite 触发器与 recursive_triggers）；删除源行前先经 kb_index 清理块（见 5.3）。

### 5.3 生命周期（钩子 + 级联 + 重建三保险）

| 事件 | 机制 |
|---|---|
| 笔记保存 | 保存收口函数（`versioned_save`；`promote_fragment_to_note` 若绕过则在其建笔记分支）后 `spawn_blocking` 静默重索引该笔记（删旧块→重切块→重 embed；单笔记毫秒~秒级） |
| 笔记/碎片删除 | db 层删除函数内**先经 kb_index 清 kb_chunks/kb_fts 再删源行**（与 `knowledge_links` 清理同款位置、同事务——`db_notes.rs:96`/`db_note_groups.rs` 先例）；FK CASCADE 仅兜底 |
| 碎片捕获 | `capture_fragment` 成功后入块（碎片不可变：一次性索引，无更新路径） |
| 全量重建 | `reindex_all` 命令（后台任务 + 进度 Channel；删除全部 kb_* → 全源重切重嵌） |
| 失败可见 | 索引失败不静默：`kb_index_stats` 报告 stale/失败计数，UI 角标「索引待重建」 |

### 5.4 混合检索（纯函数，TDD）

`kb_search(query, filters, k)` = FTS5 BM25 top-K ∪ 向量余弦 top-K（无 embedding 时跳过）→ **RRF 融合**（k=60）→ 节级 snippet 生成（命中词高亮标记，复用现有高亮渲染协议）→ 返回 `KbHit { chunk_id, note_id/fragment_id, note_title, group_name?, heading, snippet, score_kind }`。LIKE 旧链（`search_notes` 等）**保留不动**（零破坏；前端既有搜索 UI 后续可选切混合，见 §十二 不做清单）。

## 六、本地 embedding：spike 门控 + 层层降级

- **接口先行**（隔离死代码红线）：`EmbeddingEngine` trait（`dims() / embed(&[String])`）；实现 `NoopEmbedding`（恒空，永远可用）→ `OnnxEmbedding`（内嵌模型）→ `OllamaEmbedding`（走既有 Provider 的本地 Ollama 端点，用户自装，零模型分发）。向量存储层只认 trait 产物：`embedding NULL = 未嵌`。
- **选型 spike（M0，v0.19.0 前置）**：候选（1）内嵌 ONNX `bge-small-zh-v1.5`（512 窗；模型分发复用 `model_registry`/下载双镜像 + `engine.rs` 常驻引擎池先例，需解决 ort 推理接入与既有 onnxruntime.dll 共存/版本对齐——spike 必测项）；（2）Ollama `/api/embeddings` 端点。评测：小型中文检索评测集（~30 条真实库内查询 × 命中判据，盲测仪器文化复用）比较命中率/延迟/分发体积；模型文件不入库。
- **降级链**：无模型 → FTS-only（检索/问答/建议全部可用，只是少了语义召回）——**索引与读路径 A/B 不依赖 embedding 交付**（v0.19.0~2 可独立发布；语义增强批 v0.19.3 由 spike 定案后实施）。

## 七、读路径 A：学习库问答「问我的学习库」（REQ-260）

### 7.1 交互与协议

- 入口：ChatPage——新会话创建处选择模式「💬 纯聊 | 📚 学习库问答」（每会话模式，`chat_sessions` 补 `retrieval INTEGER NOT NULL DEFAULT 0` 列，ensure_column 迁移）；已有会话不改语义。
- 发送流：`chat_send(session_id, content, channel)`（既有签名；按会话 `retrieval=1` 进入学习库分支）→ 本地 `kb_search` top-K（预算内）→ **命中片段列表恒返回**（本地零成本能力，不受 AI 闸门约束）→ 若生成可用（content_gate enabled+authorized **且** `kb_qa_enabled` 开启）→ 片段打包（**复用 `budget_allocator::pack_fragments`（预留 dead_code 转正）** + `truncate_retrieval` 预算截断）→ 提示词注入（系统指令：仅依据片段回答、无命中明说"库内未找到"）→ 云端流式生成 → 回答 + `citations`（`[{noteId,noteTitle,heading,snippet,chunkId}]`）落 `chat_messages.meta_json`（与 `trajectory_json` ensure_column 同款）。产物两段：命中列表（恒有）＋ 生成回答（闸门开时）；协议事件 hits→stream 在实现批细化。
- 展示：assistant 消息下渲染**引用 chips**（「📄 笔记 · 节标题」）→ 点击跨页打开笔记并高亮命中词（复用 NotesPage 既有高亮渲染 + 路由链；跳转实现最小面 = open note + terms 高亮）。
- `/` 命令别名：`/ask`（与 v0.16.1 命令解析同构，下批接线，不阻塞本路径）。

### 7.2 治理（沿用硬约束）

预算档位复用 `budget_allocator`（轻量/标准/深度；检索片段 ≤ 档位硬顶、诚实截断不静默）；token/成本入 `ai_usage`；审计沿用 chat 链路（消息全文即轨迹，`meta_json` 存检索片段概要——AI 对话页直接可见）；上传仅授权后最小检索片段（与 ADR-010 一致）；首次云端生成前提示沿用。

### 7.3 降级

断网/Provider 故障（闸门曾开）→ 该条消息回退**命中片段列表** + 诚实错误提示（重试沿用）——"AI 问答不可用 → 检索已在"承诺的产品化；无 embedding → 命中与生成均在 FTS-only 精度上工作（设置页引擎状态可见）。

## 八、读路径 B：检索建议（发现路径，C 的良性内核）（REQ-261）

- **证据候选**（每体系实体独立现算）：概念/节点详情（`KnowledgeDetailPanel`）新增「📎 相关素材建议」区——以概念名/要点文本（concept name+essence）为查询做混合检索 top-K（≤10），**排除已链接 target**（`list_links_by_target` 过滤），逐条展示 snippet + 命中理由；勾选 → 确认 → 复用既有 `link_knowledge_target`（concept_id/node_id → note/fragment，**白名单零迁移**）落库即体系页可见。**建议不落库、零双写；确认才写**（ADR-024 纪律）。
- **相似概念候选**（跨体系交叉点）：概念名+essence embedding 近邻（或词法同名/近名兜底）→ 详情区「⚠ 可能与已有概念相似」提示（默认关）——**提示型**：仅展示（"概念 X 与体系 Y 的概念 Z 高度相似"），不自动合并（合并命令不存在且语义归人，YAGNI）；人工自行处置。
- 开关：Settings「学习库」段 `kb_discovery` 默认关（延续交叉点派生提示默认关；feature_flags 机制注册）。
- 性能：证据候选按实体现算（个人量级 <100ms），无后台批处理、无自动聚类任务。

## 九、治理（延续铁律）

1. **默认关**：读路径 A **生成**（kb_qa + content_gate 双闸门）、读路径 B（kb_discovery）均默认关；**命中片段列表为本地能力恒可用**（零成本、零上传，不受闸门约束——本地优先承诺兑现）；本地索引与 FTS5 检索恒开。
2. **预算硬顶**：A 路径复用 budget_allocator 档位；超限截断 + 诚实提示。
3. **成本/审计**：ai_usage + 轨迹可见 + 首次云端提示（复用 v0.16 授权流）。
4. **降级**：无 AI → 命中列表；无 embedding → FTS-only；索引失败 → 角标可见 + 可重建，不阻塞主链路。
5. **红线**：不接 agent 框架/记忆模块/自主 RAG 管线；向量/检索产物不直接写结构层；不自动建体系/概念/链接（人类确认）；不上传非授权数据（检索在本地完成，仅最小命中片段可上云）。
6. **与体系哲学不冲突条款**：检索建议 ≠ AI 自动写决策/自动建体系；问答输出为"找回证据"服务，不冒充"人类判断领地"。

## 十、组件与命令（新增清单）

**后端**：纯函数/db 层 `kb_index.rs`（节级切块/重索引/影子表双写）· `kb_fts.rs`（BM25 查询）· `kb_embed.rs`（EmbeddingEngine trait + Noop/Onnx/Ollama 实现）；命令层 `commands_kb.rs`（`kb_search`/`reindex_all`/`kb_index_stats`/embedding 模型下载与状态——复用 model_registry 分发）；`commands_ai_chat.rs`（chat_send retrieval 分支 + kb_qa 闸门 + pack_fragments 转正接线）；`commands_kb_discovery.rs`（证据候选/相似概念候选 + 排除已链接过滤）
**前端**：ChatPage 新会话模式选择 + CitationChips（引用跳转+高亮）· KnowledgeDetailPanel「相关素材建议」区 + 确认勾选流 · SettingsPage「学习库」段（引擎状态/模型下载按钮/索引统计与重建/发现开关——复用 ModelDiskPanel/speaker 下载 UI 范式）

## 十一、测试与验收

- **纯函数 TDD（AAA golden）**：切块器（标题切分/800 硬切/char 范围边界/空文）；RRF 融合（空集/单侧/双侧/并列）；snippet 高亮；budget 截断复用测试；证据候选排除已链接
- **db 层**：kb_chunks FK 级联（note/fragment 删除）；FTS 影子表同步（增删改）；kb_meta 幂等
- **命令层**：chat_send retrieval 分支（双闸门路径：未开/未授权拒绝；无 AI 降级命中列表；无 embedding 降级 FTS-only）；kb_search 过滤/上限；discovery 确认流落库（复用 link 幂等语义）
- **模型相关**：embedding 集成测试单独标注（不依赖真实模型文件的单测纪律）
- **前端 Vitest**：模式选择与闸门空态；引用 chips 渲染/点击跳转 mock；发现区勾选确认流
- **验收（用户）**：① 学习库问答模式开箱即用：发送即得本地命中片段列表（笔记/节引用）；AI 未开 → 生成区引导直达设置（不灰死）② 开启 AI 后：问"我在哪学过 XX"→ 命中列表 + 带引用生成回答；点引用跳笔记高亮命中词 ③ 断网/Provider 故障 → 该条回退命中列表 + 诚实错误可重试 ④ 删除/编辑笔记后索引即时一致；重建按钮可全量修复 ⑤ 概念详情「相关素材建议」（开关开启后）→ 勾选确认 → 体系页链接即现；未确认不落库 ⑥ 每问成本/轨迹可见（ai_usage + 消息全文 + meta_json）⑦ 无 embedding 模型时 ①②⑤ 以 FTS 精度工作（设置页引擎状态如实显示）⑧ 回归：cargo test / clippy / vitest / tsc 全绿

## 十二、冲突条款修订与登记衔接

1. **REQ-231（L3 全库检索）/ REQ-024（问我的笔记）**：本设计落地主体 = REQ-260 + REQ-258；v0.10.0 #15 "依赖本地 FTS5 检索" 兑现口径由 LIKE 升级为 FTS5（如实登记：此前仅 LIKE）。
2. **X1 课程级知识库（V1.0）**：检索面由本设计前置合流（kb_search 跨笔记/碎片即跨会话知识检索的最小实现）；课程级聚合（重复合并/术语总库/统一大纲）仍属 X1 主体，不提前。
3. **O5/C8 跨会话 embedding 去重**：此前因"无本地 embedding 选型"搁置——本设计 spike（§六）落地后即为前置条件满足；是否立项由 X1 波次裁决，本设计不做自动合并。
4. **不做清单**：不改既有 LIKE 搜索命令/UI；不做会话原文/OCR 原料检索（REQ-023 远期）；不做自动概念合并/自动体系写入；不做云端向量库/外部检索服务（本地量级无需）；不做流式 RAG 增量索引（保存后整篇重索引已够）；不做图片/多模态检索（REQ-093/094 另行）。
