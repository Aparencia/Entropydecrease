# 课伴 v0.3.0 版本迭代计划

> **版本**：v0.3.0  
> **阶段**：MVP-1 打磨期  
> **状态**：规划中  
> **创建日期**：2026-07-09  
> **最后更新**：2026-07-09

---

## 一、版本概述

### 1.1 v0.3.0 定位

课伴 v0.2.0（MVP-1 Alpha 完成态）已交付四大核心模块（番茄钟、智能笔记、闪卡、费曼学习法）的基础功能。基于用户实际使用反馈，收集到 **22 项原始需求 + 2 项新增需求**，共计 **24 项待处理需求**。经过三轮产品头脑风暴讨论，完成需求澄清、可行性分析和 MoSCoW 优先级分类。

| 版本 | 定位 | 状态 |
|------|------|------|
| v0.2.0 | MVP-1 Alpha 完成态 — 四大核心模块本地功能可用 | ✅ 已交付 |
| **v0.3.0** | **MVP-1 打磨版 — Bug 修复 + 体验优化 + 功能增强 + 增值功能 + AI 体验增强** | 🔄 规划中 |
| v2.0+ | MVP-2 — 云同步引擎 + AI 增强 + 双模式框架 | ✅ 已交付 |

### 1.2 与 MVP-1 / MVP-2 的关系

根据 [MoSCoW 优先级矩阵](../../phase1/03-MoSCoW优先级矩阵.md) 中的迭代交付路线图：

- **v0.3.0 属于"MVP-1 打磨 v1.0~v1.2"阶段**（预计 4-6 周的 Bug 修复、性能优化、用户反馈迭代）
- v0.3.0 的 Must Have 需求是对 MVP-1 核心功能的补全和修复
- v0.3.0 的 Should Have / Could Have 需求是从用户反馈中提炼的高价值增强项

根据 [里程碑计划](../../phase2/01-里程碑计划.md) 中的两阶段交付策略，v0.3.0 属于 **MVP-1 和 MVP-2 均交付之后的迭代打磨阶段**，在已交付的基础上进一步优化本地功能体验。

### 1.3 迭代目标

| 目标维度 | 说明 |
|---------|------|
| **Bug 修复** | 修复番茄钟计数重置、应用图标、保存状态等影响基本体验的缺陷 |
| **低成本 UI 改进** | 侧边栏折叠、信息密度预览、自定义右键菜单等零架构变更的体验优化 |
| **功能增强** | 番茄钟全面升级（目标功能、图表统计、音频系统）、编辑器扩展、笔记模板差异化、打卡系统 |
| **AI 体验增强** | AI 摘要后续操作面板（内联上下文操作 + 智能建议卡片），提升已交付 AI 功能的交互深度 |
| **增值功能** | 思维导图可视化、窗口监视、学习浮窗、成就系统、灵感空间等高级功能 |
| **架构深化** | 在 MVP-2 已交付的 IRepository / operationLog 基础上持续优化，不实现云端同步 |

### 1.4 边界声明

- **v0.3.0 不涉及 MVP-2 已交付内容的重新开发**：云同步引擎、AI 增强功能（AI 摘要/续写/智能卡片生成）、双模式框架已在 MVP-2 中交付，v0.3.0 仅聚焦本地功能体验优化和 AI 交互增强
- **仅做架构预留**：`IRepository` 接口已抽象，`operationLog` 表已存在，为未来增量同步提供基础；牌组分享文件（.kban-deck）作为社区功能的手动 MVP 验证分享需求
- 参见 [系统架构设计](../../phase3/01-系统架构设计.md) 中的本地优先架构理念和 [技术选型决策记录](../../phase3/02-技术选型决策记录ADR.md) 中的技术栈选型

# 课伴 v0.3.0 需求分析与变更追踪

## 一、需求来源与背景

### 1.1 用户反馈收集过程

课伴 v0.2.0（MVP-1 Alpha 完成态）交付后，通过实际使用测试收集到 **22 项原始需求**。在后续需求整理过程中，经用户补充提出 **2 项新增需求**，共计 **24 项待处理需求**。

需求来源覆盖以下维度：

- **Bug 修复**：番茄钟计数重置、应用图标缺失、保存状态无反馈等影响基本体验的缺陷
- **体验优化**：侧边栏折叠、信息密度预览、自定义右键菜单等 UI 交互改进
- **功能增强**：番茄钟目标功能、图表化统计、音频系统、打卡系统等用户高频诉求
- **增值功能**：思维导图可视化、窗口监视、学习浮窗、成就系统等差异化竞争力功能

### 1.2 三轮产品头脑风暴讨论

针对 24 项原始需求，进行了三轮产品头脑风暴讨论：

1. **第一轮：需求澄清** — 逐项确认需求的真实意图，消除歧义，合并重复项，界定需求边界
2. **第二轮：可行性分析** — 评估每项需求的技术可行性、复杂度、依赖关系和潜在风险
3. **第三轮：优先级分类** — 使用 MoSCoW 方法对需求进行优先级分级，确定交付版本

### 1.3 需求澄清与可行性分析结果

经过澄清与分析，形成以下决策：

- 24 项需求中，**6 项 Must Have**、**8 项 Should Have**、**11 项 Could Have** 纳入 v0.3.0 交付范围
- **6 项 Won't Have** 需求记入 Backlog，不在 v0.3.0 范围内实现
- 采用三个子版本（alpha.1 → alpha.2 → beta）递进交付策略
- 详细迭代计划参见 [01-版本迭代计划](./01-版本迭代计划.md)

## 四、需求优先级排序依据

### 4.1 RICE 评分框架说明

采用 RICE 评分框架对需求进行量化评估，各维度定义如下：

| 维度 | 含义 | v0.3.0 评估标准 |
|------|------|----------------|
| **Reach（触达范围）** | 该功能影响的用户比例 | 基于 v0.2.0 用户反馈中提及该需求的频率 |
| **Impact（影响程度）** | 对用户体验的提升幅度 | 3 = 巨大 / 2 = 高 / 1 = 中 / 0.5 = 低 / 0.25 = 极低 |
| **Confidence（信心水平）** | 对评估准确性的信心 | 100% = 高信心 / 80% = 中信心 / 50% = 低信心 |
| **Effort（工作量）** | 预估开发人天 | 以"人天"为单位，值越低优先级越高 |

**RICE 评分公式**：`RICE Score = (Reach × Impact × Confidence) / Effort`

### 4.2 Must Have 需求 RICE 评估

| 编号 | 需求名称 | Reach | Impact | Confidence | Effort | RICE Score | 排序理由 |
|------|---------|-------|--------|------------|--------|------------|---------|
| M1 | 番茄钟计数重置 Bug 修复 | 100% | 2 | 100% | 0.5 天 | **400** | 核心功能 Bug，影响所有番茄钟用户，修复成本极低 |
| M2 | 应用图标修正 | 100% | 1 | 100% | 0.5 天 | **200** | 品牌基本形象，所有用户可见，修复成本极低 |
| M3 | 保存提示 | 80% | 2 | 100% | 0.5 天 | **320** | 数据安全感缺失是高频痛点，修复成本低 |
| M4 | AI 配置位置 | 60% | 1 | 100% | 0.5 天 | **120** | AI 功能可用性的前提，但当前 AI 使用率较低 |
| M5 | 侧边栏收回能力 | 100% | 2 | 100% | 1 天 | **200** | 全局 UI 改进，所有用户受益，实现成本可控 |
| M6 | 番茄目标 | 80% | 2 | 80% | 2 天 | **64** | 提升番茄钟使用目的性，用户高频诉求 |

### 4.3 排序决策理由

1. **Bug 修复优先**：M1（番茄钟计数重置）为功能性 Bug，直接影响核心模块的正确运行，RICE 评分最高（400），必须在 alpha.1 首先修复
2. **低成本高收益优先**：M2（图标）、M3（保存提示）、M4（AI 配置）均为半天工作量即可完成的改进，快速交付可提升用户信心
3. **Must Have 全部在 alpha 阶段完成**：M1~M5 在 alpha.1 交付，M6 在 alpha.2 交付，确保 Must Have 需求在进入 beta 前全部闭环
4. **Should Have 按依赖关系排序**：S1/S3 无依赖，在 alpha.1 并行交付；S2→S4、S6→S7 有依赖关系，在 alpha.2 按序交付
5. **Could Have 统一放入 beta**：beta 阶段允许裁剪，可根据 alpha 阶段的用户反馈动态调整优先级

## 二、逐任务技术设计

### Task 1.1 番茄钟计数重置 Bug 修复 (M1)

#### 现状分析

`usePomodoroStore.ts` 中 `completedCount` 用于追踪已完成的番茄钟数量，以决定下一次休息是短休还是长休。当前实现在长休（long_break）结束后，`completedCount` 未重置为 0，导致 `getNextPhase()` 中 `(completedCount + 1) % longBreakInterval` 计算结果错误，后续长休间隔不再符合用户设定的 `longBreakInterval`（默认 4）。

#### Bug 根因

```typescript
// 当前逻辑（有 Bug）
getNextPhase(): Phase {
  if (phase === 'work') {
    return (completedCount + 1) % longBreakInterval === 0
      ? 'long_break'
      : 'short_break';
  }
  return 'work';
}
```

长休结束后 `completedCount` 未归零，例如完成 4 个番茄后 `completedCount = 4`，长休结束后仍为 4，下一轮第 5 个番茄完成时 `(4+1) % 4 = 1 ≠ 0`，不会触发长休。

#### 修改方案

在 `tick()` 和 `skip()` 的状态更新逻辑中，当检测到 `phase === 'long_break' && nextPhase === 'work'` 时，同步将 `completedCount` 重置为 0：

```typescript
// 修复方案
if (currentPhase === 'long_break' && nextPhase === 'work') {
  set({ completedCount: 0, phase: nextPhase });
}
```

| `client/src/features/pomodoro/store/usePomodoroStore.test.ts` | 新增回归测试用例 |

新增 4 个回归测试用例：

2. 长休后重新开始，第 4 个番茄再次触发长休

### Task 1.7 锁定右键菜单 (S3)

#### 现状分析

Electron 桌面应用默认右键菜单会弹出浏览器原生上下文菜单（包含"检查元素"、"重新加载"等开发选项），对学习工具类产品而言体验不佳，且可能暴露开发信息。需要锁定原生右键菜单，同时保留编辑器区域的正常右键功能，并为特定 UI 元素提供自定义上下文菜单。

#### 修改方案

**全局右键拦截（main.tsx）**：

```typescript
// 全局拦截原生右键菜单
document.addEventListener('contextmenu', (e: MouseEvent) => {
  const target = e.target as HTMLElement;

  // 白名单：允许原生右键的区域
  const whitelist = [
    '.ProseMirror',           // TipTap 编辑器
    '[contenteditable]',      // 可编辑区域
    'input',                  // 输入框
    'textarea',               // 文本域
  ];

  const isWhitelisted = whitelist.some((selector) => target.closest(selector));
  const isAllowed = target.closest('[data-allow-context-menu]');

  if (!isWhitelisted && !isAllowed) {
    e.preventDefault();
  }
});
```

**新建 ContextMenu.tsx 组件**：
- 使用 React Portal 渲染到 `document.body`，避免被父容器 `overflow: hidden` 裁切
- 监听全局 `contextmenu` 事件，当非白名单区域被右键时显示自定义菜单
- 支持 `Escape` 键关闭菜单
- 点击菜单外部区域自动关闭
- 菜单项根据右键目标类型动态调整（如牌组卡片显示"删除/重命名"，通用区域显示"刷新"）

**FlashcardsPage 集成**：
- 在牌组卡片元素上添加 `data-allow-context-menu` 属性，使其触发自定义上下文菜单而非被完全拦截

```typescript
async function calculateStreak(db: DexieDatabase): Promise<number> {
  const yesterday = format(subDays(new Date(), 1), 'yyyy-MM-dd');
  const lastRecord = await db.studyCheckIns.get(yesterday);
  return lastRecord ? lastRecord.streakDays + 1 : 1;
}
```

跨日零点自动判断，断签后重置为 1。

- 今日打卡状态（已打卡 / 未打卡）

## 四、Dexie Schema v4 迁移方案

### 4.1 新增表定义

```typescript

this.version(4).stores({
```

### 4.2 迁移策略

- 遵循已有版本迁移模式：逐表 + try/catch
- Schema v3 → v4 为纯新增表，无现有表结构变更，数据丢失风险极低
- 迁移失败时记录错误日志，不阻塞应用启动
- Alpha 阶段用户极少，迁移影响范围可控

### 4.3 索引说明

| 表 | 索引 | 说明 |
|----|------|------|
| `studyCheckIns` | `id` (PK), `&date` (unique) | date 唯一确保每日仅一条记录 |
| `achievements` | `id` (PK), `&key` (unique) | key 唯一确保成就不重复解锁 |
| `pomodoroGoals` | `id` (PK), `text` | 按文字内容查询去重 |

### Task 3.1 思维导图只读可视化 (C1)

#### 现状分析

当前笔记模块支持标准富文本和康奈尔模板，但缺少思维导图可视化展示能力。部分用户希望将层级化的 bulletList 内容以树形图形式直观呈现，便于全局把握知识结构。

完整版思维导图（可拖拽编辑、多分支、颜色主题）工程量极大，已列入 Won't Have（W3）。0.3.0 beta 仅实现**只读可视化**的最小版本。

#### 修改方案

**模板标识**：新增 `template: 'mindmap'` 笔记类型。

当 `note.template === 'mindmap'` 时，`NoteEditPage.tsx` 条件渲染 `MindMapCanvas` 组件替代默认 TipTap 编辑器。

**MindMapCanvas 组件设计**：

```
┌──────────────────────────────────────────────────┐
│  思维导图可视化（MindMapCanvas）                     │
│                                                  │
│              ┌───────┐                           │
│              │ 根节点 │                           │
│              └───┬───┘                           │
│         ┌────┬─┴──┬────┐                       │
│         │    │     │    │                       │
│      ┌─┴─┐ ┌┴─┐ ┌─┴─┐ ┌┴─┐                  │
│      │子A│ │子B│ │子C│ │子D│                  │
│      └─┬─┘ └─┬─┘ └───┘ └───┘                  │
│        │     │                                 │
│     ┌─┴─┐ ┌─┴─┐                              │
│     │孙1│ │孙2│                              │
│     └───┘ └───┘                              │
└──────────────────────────────────────────────────┘
```

**数据转换**：
- 读取 TipTap bulletList JSON 结构，递归解析为树形数据
- 每个 `listItem` 对应一个节点，嵌套的 `bulletList` 对应子节点

**渲染方案**：
- 采用 SVG 渲染，轻量级，无需引入额外依赖
- 使用简单的递归布局算法：根节点居中，子节点按层级向外展开
- 节点之间使用贝塞尔曲线连接
- 节点样式：圆角矩形 + 文字，根节点突出显示

**交互设计**：
- **只读展示**：不支持拖拽编辑节点内容或位置
- **缩放**：Ctrl + 滚轮缩放 SVG 视口
- **平移**：按住空白区域拖拽移动视口
- **折叠/展开**：点击节点可折叠/展开子节点
- **编辑入口**：提供“切换为列表编辑”按钮，跳转回 TipTap bulletList 编辑模式

**技术实现**：
- SVG 容器：`<svg>` 元素配合 `viewBox` 实现缩放平移
- 布局算法：简单的递归树形布局，每层节点水平排列，层间垂直间距
- 数据来源：从 `note.content`（TipTap JSON）中提取 bulletList 结构

### Task 3.2 窗口监视 + 学习浮窗 (C2 + C3)

#### 现状分析

当前应用无法感知用户是否真正在专注学习，用户可能在番茄钟运行期间切换到娱乐应用。同时，番茄钟界面占据主窗口，用户无法在学习时查看倒计时。

C2（窗口监视）和 C3（学习浮窗）紧密耦合，C3 依赖 C2 的专注状态判断。C2 先行实现，C3 在此基础上构建。

#### 修改方案

**C2 窗口监视**：

**Electron 主进程窗口监视**：
- `client/electron/main.ts` 新增窗口监视逻辑，使用 Node.js `child_process` 调用系统命令（如 PowerShell `Get-Process`）获取前台窗口信息
- `client/electron/preload.ts` 通过 IPC 暴露 `getActiveWindowInfo()` 方法，返回前台窗口标题和进程名
- 白名单配置存储在 localStorage，用户可添加学习相关应用名称

**前端轮询**：
- 新建 `useActiveWindow.ts` hook，每 3-5 秒通过 IPC 调用主进程获取当前窗口信息
- 维护专注/走神状态：当前窗口不在白名单内且番茄钟正在运行时判定为“走神”
- 走神时温和提醒：主窗口内显示非侵入式 Toast（“检测到您已离开学习窗口，是否继续专注？”）
- 事后统计：记录每次走神的时间段和持续时长，存入番茄会话记录

**C3 学习浮窗**：

**Electron 多窗口配置**：
- 使用 `BrowserWindow` API 创建浮窗窗口：320x200、`alwaysOnTop: true`、无装饰栏
- 浮窗显示内容：番茄倒计时、当前阶段、暂停/跳过按钮、返回主窗口按钮

**浮窗触发**：
- 番茄钟启动时可选择“开启浮窗模式”
- 主窗口最小化时浮窗自动显示

**PWA 降级方案**：
- 窗口监视和浮窗功能仅 Electron 桌面端可用
- PWA 模式下隐藏“窗口监视”和“浮窗”入口，显示“仅桌面端支持”提示
- 通过 `useMode()` hook 判断当前运行环境

### Task 3.10 自由笔记基础版 (C11)

#### 现状分析

当前笔记模块支持标准富文本（`template: 'standard'`）和康奈尔（`template: 'cornell'`）模板，所有内容均为自上而下的线性文档结构。部分用户有"随意摆放笔记块"的需求，希望在一个自由画布上拖拽放置文本块，类似简化版 OneNote 或 Miro。

完整版自由笔记（OneNote 式画布：手写、图片、形状、多页）工程量极大，已列入 Won't Have（W1）。0.3.0 beta 仅实现**文本块自由拖拽**的最小版本。

#### 修改方案

**模板标识**：新增 `template: 'free'` 笔记类型。

当 `note.template === 'free'` 时，`NoteEditPage.tsx` 条件渲染 `FreeCanvas` 组件替代默认 TipTap 编辑器。

**FreeCanvas 组件设计**：

```
┌──────────────────────────────────────────────────┐
│  自由画布（FreeCanvas）                            │
│                                                  │
│   ┌─────────┐          ┌─────────┐              │
│   │ 文本块A │          │ 文本块B │              │
│   │ (可拖拽) │          │ (可拖拽) │              │
│   └─────────┘          └─────────┘              │
│                                                  │
│          ┌─────────┐                             │
│          │ 文本块C │                             │
│          │ (可拖拽) │                             │
│          └─────────┘                             │
│                                                  │
│   [+ 添加文本块]                                  │
└──────────────────────────────────────────────────┘
```

**数据模型**：

```typescript
interface FreeCanvasBlock {
  id: string;
  type: 'text';           // 0.3.0 仅支持文本块
  content: string;        // TipTap JSON 或纯文本
  position: {
    x: number;            // 相对画布左上角的 X 坐标
    y: number;            // 相对画布左上角的 Y 坐标
  };
  size: {
    width: number;        // 块宽度（px）
    height: number;       // 块高度（px），'auto' 则自适应内容
  };
}

interface FreeCanvasData {
  blocks: FreeCanvasBlock[];
  canvasWidth: number;    // 画布宽度（默认 2000px）
  canvasHeight: number;   // 画布高度（默认 2000px）
}
```

笔记内容存储为 `FreeCanvasData` JSON，存入笔记的 `content` 字段。

**交互设计**：
- **添加文本块**：底部"+ 添加文本块"按钮，新块出现在画布中央
- **拖拽移动**：文本块标题栏/顶部拖拽手柄，鼠标拖拽改变 `position.x/y`
- **文本编辑**：每个文本块内嵌一个轻量 TipTap 实例（仅基础编辑，不含表格/图片等高级扩展）
- **缩放/调整大小**：文本块右下角拖拽调整 `size.width/height`
- **删除文本块**：选中后 Delete 键或右上角关闭按钮
- **画布平移**：按住空白区域拖拽移动画布视口（CSS `transform: translate`）

**技术实现**：
- 画布容器：`position: relative`，固定尺寸（2000x2000），外层 `overflow: auto` 滚动
- 文本块：`position: absolute`，通过 `left/top` 定位到 `block.position.x/y`
- 拖拽：原生 `mousedown/mousemove/mouseup` 事件，不引入额外拖拽库
- 每个文本块的 TipTap 实例在组件挂载时创建，卸载时销毁
- 内容变更通过 `debouncedSave` 自动保存（复用现有保存机制）

**限制（0.3.0 不做）**：
- 不支持手写/绘图
- 不支持图片块、形状块
- 不支持多页画布
- 不支持文本块之间的连线/关联
- 不支持撤销/重做（依赖 TipTap 内置 history 扩展）

## 一、测试分层策略

参照 [测试规范与流程](../../phase5/01-测试规范与流程.md) 中的测试金字塔定义，结合 v0.3.0 三个子版本的递进交付特点，定义如下测试分层：

| 层级 | 类型 | 工具 | 覆盖率目标 | 执行频率 |
|------|------|------|-----------|---------|
| L1 | 单元测试 | Vitest | ≥80% | 每次提交 |
| L2 | 集成测试 | Vitest + @testing-library/react | 核心路径 | 每次 MR |
| L3 | 系统测试 | Playwright（可选） | 核心流程 | 发版前 |
| L4 | UAT | 手动验收 | Exit Criteria | 子版本发布前 |
| L5 | 回归测试 | 全量自动化 + 手动 | 全量 | 每次发版 |

### 1.1 各层级职责说明

- **L1 单元测试**：覆盖纯逻辑模块（Zustand store、SM-2 算法、打卡计算、音频控制 hook、Dexie 迁移脚本），要求行覆盖率 ≥80%
- **L2 集成测试**：覆盖组件交互路径（番茄钟阶段切换 UI、编辑器保存流程、侧边栏折叠状态同步），使用 `@testing-library/react` 渲染组件并验证 DOM 行为
- **L3 系统测试**：覆盖端到端核心流程（创建笔记→编辑→保存→查看、番茄钟完整工作循环），发版前执行
- **L4 UAT 验收**：由产品/用户按 Exit Criteria 检查项逐条手动验证
- **L5 回归测试**：全量自动化用例 + 关键路径手动验证，确保新版本不破坏已有功能

### 1.2 测试原则

- **测试左移**：需求阶段即编写验收标准（见本文第五节 Exit Criteria）
- **自动化优先**：能自动化的测试不手动执行
- **快速反馈**：单元测试执行时间 < 30 秒
- **增量覆盖**：每个子版本新增代码必须附带对应测试

```typescript
import { describe, it, expect, beforeEach } from 'vitest';
import { usePomodoroStore } from './usePomodoroStore';

describe('usePomodoroStore', () => {
  beforeEach(() => {
    // 重置 store 状态
    usePomodoroStore.setState({
      completedCount: 0,
      phase: 'work',
      // ...
    });
  });

  describe('阶段切换', () => {
    it('should 完成 4 个番茄后进入长休', () => {
      const store = usePomodoroStore.getState();
      // 模拟完成 4 个番茄
      for (let i = 0; i < 4; i++) {
        store.completePomodoro();
      }
      expect(usePomodoroStore.getState().phase).toBe('longBreak');
    });

    it('should 长休后重置 completedCount 为 0', () => {
      const store = usePomodoroStore.getState();
      // 完成 4 个番茄 + 长休结束
      for (let i = 0; i < 4; i++) {
        store.completePomodoro();
      }
      store.completeBreak();
      expect(usePomodoroStore.getState().completedCount).toBe(0);
    });

    it('should 模式切换时保持 completedCount', () => {
      const store = usePomodoroStore.getState();
      store.completePomodoro();
      store.completePomodoro();
      expect(usePomodoroStore.getState().completedCount).toBe(2);
      // 切换模式不影响计数
    });
  });
});
```

1. 确认通用 Checklist 和对应子版本专项检查全部通过
2. 同步版本号（package.json、electron-builder.yml）
3. 创建 Git tag：`git tag v0.3.0-alpha.1`（或 alpha.2 / beta）
4. 执行 `npm run build`，部署 dist/ 到 PWA 服务器
5. 执行 `npm run electron:build`，生成 NSIS 安装包
6. 在 GitHub Releases 创建 Release，上传安装包和校验和
7. 编写并发布发布说明

### 6.1 PWA 回滚

- 部署上一版本的 dist/ 文件到 CDN/服务器
- Service Worker 自动检测版本变化并回退

- Dexie Schema 迁移脚本支持回退（谨慎使用）
