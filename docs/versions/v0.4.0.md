## 三、核心技术架构决策

### 决策 1：AI 错误处理 — 在 AIPluginLoader 单例中统一拦截

**现状**：内容长度校验分散在 `ElectronAIPlugin.ts`(L33) 和 `RemoteAIPlugin.ts`(L21)，`useAI.ts` 的 catch 块无法区分错误类型。

**方案**：在 `AIPluginLoader.ts` 中新增 `private async withGuard()` 包装方法，统一处理：
- 内容长度前置校验（`content_too_short`）
- 网络在线检查（`navigator.onLine`）
- 错误分类（timeout / service_unavailable / offline）

删除两个插件中重复的长度校验，`useAI.ts` 的 catch 块根据 `error.code` 显示差异化 Toast。

**关键文件**：
- `client/src/lib/ai/AIPluginLoader.ts`（98 行）— 核心拦截点
- `client/src/lib/ai/types.ts`（L104-113）— AIError.code 枚举扩展
- `client/src/lib/ai/useAI.ts`（111 行）— 4 个 hook 的 catch 分支
- `client/src/lib/ai/ElectronAIPlugin.ts`（L33-34）— 删除重复校验
- `client/src/lib/ai/RemoteAIPlugin.ts`（L21-22）— 删除重复校验

### 决策 2：右键菜单 — ContextMenu 2.0 + 声明式注册

**现状**：`ContextMenu.tsx`（102 行）已有 Portal 渲染、边界检测、Escape 关闭，但仅支持扁平 items，无分组能力。

**方案**：
1. 扩展接口：新增 `ContextMenuGroup { label?: string; items: ContextMenuItem[] }`，保留原 `items` prop 向后兼容
2. 新建 `useContextMenu.ts` hook 封装 `onContextMenu` 事件 + 状态管理
3. 各模块通过声明式配置注册菜单项

**向后兼容**：原 `items: ContextMenuItem[]` 内部自动包装为单 group `[ { items } ]`。

### 决策 3：动画 — 纯 CSS + Tailwind，不引入 Framer Motion

**现状**：`tokens.css` 已有完整动效令牌，`FlipCard` 已实现 3D 翻转。Framer Motion 全量 ~35KB gzipped。

**方案**：扩展 `tokens.css` 和 `tailwind.config.js`：
- 新增 `--kb-ease-bounce: cubic-bezier(0.34, 1.56, 0.64, 1)` 物理回弹
- 新增 `@keyframes scale-bounce`、`stagger-in`、`pulse-skeleton`
- 所有动画仅使用 `transform` 和 `opacity`（GPU 合成层）
- 保留 `prefers-reduced-motion` 媒体查询

### 决策 4：数据库 Schema — v0.4.0 采用 clear+reinsert + 双版本兼容模式迁移

**方案**：Dexie Schema 从 v4 升级到 v5，采用 **clear+reinsert + 双版本兼容模式**，迁移期间同时兼容 v4 和 v5 版本。

**迁移内容**：
1. **新增 `videoNoteType` 字段**：笔记数据模型增加模板类型标识，区分普通笔记与网课笔记
2. **新建 `windowCaptures` 表**：存储屏幕截图元数据及 AI 提取结果（混合方案数据存储）
3. **清理 flashcards 表空字段**：移除历史遗留的空值字段，精简数据结构
4. **迁移 C11 自由笔记/课程笔记**：将 v0.3.0-beta 交付的自由笔记基础版数据迁移至新 Schema，确保用户已有笔记在 v5 结构下完整保留

**风险控制**：迁移脚本执行前自动备份全量数据；clear+reinsert 过程中保持 v4 版本数据库可读，失败时可回滚；不修改已有表结构（仅清理空字段和新增字段/表）。

**推迟项**：`sourceNoteId`（笔记-闪卡双向关联）仍推迟至 v0.5.0。v0.5.0 前置准备：右键菜单中"查看上下文"先置灰显示 "Coming Soon"。

### 决策 5：登录模式 — 仅做 AuthGuard 软提醒

**方案**：新建 `AuthGuard.tsx` 路由守卫，默认 pass-through（不阻断），仅在 Supabase 凭证有效且用户主动选择登录时才拦截。占位符凭证时完全跳过。

### 决策 6：网课笔记混合方案 — OS 原生 + AI 多模态混合架构

**背景**：混合方案（方案E）在功能完整性和准确率上达到最优，但开发工期长（12-18 周）、端到端延迟较高（2-5s）、CPU 开销较大（5-15%）。高效落地的关键在于"智能路由调度"和"异步解耦架构"。

**核心技术路线**：**OS 原生能力 + AI 多模态混合**，不依赖 PaddleOCR/Whisper 等本地重量级模型，而是充分利用操作系统原生能力和多模态 AI 模型进行视觉理解与文本提取。

**核心模块**：

1. **采集层**（极低开销）：Electron `desktopCapturer` 定时截图 + WASAPI 系统音频切片，两者独立运行，仅负责往缓冲区推数据
2. **异步处理流水线**：多模态 AI 视觉提取（GLM-4V-Flash/Qwen-VL-Plus）、ASR（阿里云 Paraformer）、UI Automation 作为独立 Worker 并行消费数据
3. **智能路由调度**：UI Automation 优先（零成本）→ 多模态 AI 视觉提取（主力）→ 按需降级策略
4. **音视频交叉融合**：VAD 驱动视觉抓取、ASR/视觉文本去重对齐、公式与语音联合校正
5. **时间戳对齐**：所有数据包打单调递增时间戳，结果融合层基于时间轴对齐

**推荐技术栈**：

| 组件 | 技术选型 |
|------|---------|
| 音频 ASR | 阿里云 Paraformer（API）/ Faster-Whisper（本地备选） |
| 视觉文本提取 | 多模态 AI 模型（GLM-4V-Flash 免费 / Qwen-VL-Plus） |
| UI 探测 | Windows UIAutomation |
| 多模态 AI | GLM-4V-Flash（免费）/ Qwen-VL-Plus |
| 变化检测 | pixelmatch / pHash |
| 调度中枢 | Electron Worker Thread + 消息队列 |

**关键文件**：
- `client/electron/screenCapture.ts`（新建）— 屏幕截图采集模块
- `client/electron/audioCapture.ts`（新建）— 系统音频采集模块
- `client/src/features/notes/components/CaptureSidebar.tsx`（新建）— 课堂助手侧边栏
- `server/ai-gateway/routers/vision.py`（新建）— 多模态 AI 视觉端点
- `server/ai-gateway/chains/vision_extract_chain.py`（新建）— 视觉提取链

## 八、被拒绝的替代方案

| 替代方案 | 拒绝理由 |
|---------|---------|
| 完整 C9 灵感空间模块 | 全新 feature 模块需路由+store+页面+AI 打标接口，回归面过大，依赖后端新增路由 |
| 数据库 Schema v5 全量重建（sourceNoteId） | Flashcard 全表重建影响用户数据完整性；v0.4.0 采用 clear+reinsert + 双版本兼容做增量变更 |
| 全局命令面板（Cmd+K） | 超出 v0.4.0 "专注体验与记录闭环" 主题 |
| 引入 Framer Motion | ~35KB gzipped 包体积增加，所有动效均可用纯 CSS 实现 |
| TipTap 扩展懒加载 | 性能优化有价值但非本版本主题，且可能引入编辑器闪烁 |
| 反馈入口仅外链 | 过于简陋，改为内嵌反馈面板（T3.6），支持本地存储 + 状态追踪 |
| 完整登录模式 / 本地账号体系 | 认证层大面积重构，风险极高 |
| AI 离线请求队列（IndexedDB 持久化） | offlineQueue 表已定义但完整实现涉及重试调度+UI 状态，推迟更安全 |
| iframe/webview 嵌入+音频转录方案 | 法律风险高：嵌入第三方网课平台违反 ToS，音频转录可能涉及版权侵权 |
| 纯网络请求拦截方案 | 违反边界约束：混合方案仅基于 OS 级窗口监听，不得通过网络拦截、DOM 解析、API 逆向等爬取手段 |
| PaddleOCR + Whisper 本地模型方案 | 本地模型体积大（PaddleOCR ~100MB、Whisper ~1GB），WASM 编译兼容性差，CPU 开销高；改用 OS 原生 + AI 多模态混合方案更轻量 |

## 四、需求优先级排序依据

### 4.1 排序原则

v0.4.0 需求优先级遵循以下排序原则：

1. **体验债务优先**：M1（AI 静默失败）和 M2（网络 Bug）是已知的核心体验缺陷，用户在使用过程中已遇到，必须首先修复
2. **导航迷失优先**：M3（全局导航）解决用户在深层页面"找不到回去的路"的痛点
3. **架构基建先行**：S1（ContextMenu 2.0 框架）是 S2（三模块菜单）的前置依赖，需在 alpha.2 首先完成
4. **低成本高收益**：S3（ComingSoon）和 S4（引导增强）工期短、独立性强，可并行快速交付
5. **动效润色收尾**：C1（CSS 动效）在功能稳定后实施，避免与功能开发交叉干扰
6. **高风险可选**：C4（托盘常驻）复杂度高且仅 Electron 端可用，标记为可选

### 4.2 排序决策理由

| 优先级 | 需求 | 理由 |
|--------|------|------|
| P0-1 | M1 AI 低字数提醒 | AI 功能静默失败导致用户困惑，是最高频的用户反馈 |
| P0-2 | M2 网络查询 Bug | 断网时超时等待体验极差，需立即感知离线状态 |
| P0-3 | M3 全局导航增强 | 深层页面导航迷失影响所有用户 |
| P0-4 | M4 应用图标 | 品牌基本形象，极低修复成本 |
| P1-1 | S1 ContextMenu 2.0 | 架构基建，S2 的前置依赖 |
| P1-2 | S2 三模块右键菜单 | 打通"记录→复习"链路的核心交互 |
| P1-3 | S3 ComingSoon | 低成本，减少用户对未开发功能的困惑 |
| P1-4 | S4 引导增强 | 低成本，提升新用户上手体验 |
| P2-1 | C1 动效增强 | 质感提升，纯 CSS 无包体积影响 |
| P2-2 | C2 SM-2 反馈 | 学习科学理论融合，提升复习效果 |
| P2-3 | C3 反馈面板 | 建立用户反馈闭环 |
| P2-4 | C4 托盘常驻 | 高风险可选项，仅桌面端 |

### T1.3 AI 低字数摘要提醒

#### 现状分析

`ElectronAIPlugin.ts`（L33）和 `RemoteAIPlugin.ts`（L21）各自在 `summarizeNote()` 方法中独立校验内容长度：

```typescript
// ElectronAIPlugin.ts L33 和 RemoteAIPlugin.ts L21（相同逻辑）
if (!noteContent || noteContent.trim().length < 10) {
  throw new AIError('笔记内容过短（至少 10 个字符），无法生成摘要', 'invalid_response', false);
}
```

存在以下问题：
1. **校验逻辑重复**：两个 Plugin 各自实现相同校验，违反 DRY
2. **错误码语义不精确**：使用 `'invalid_response'` 表示内容过短，语义不匹配
3. **`AIPluginLoader.ts`（98 行）无统一拦截**：`summarizeNote()`（L64）、`generateFlashcards()`（L72）、`evaluateExplanation()`（L79）直接透传到 Plugin，无前置校验
4. **`useAI.ts`（111 行）4 个 hook 的 catch 块**无法区分错误类型，统一调用 `getLocalFallbackMessage()` 返回通用降级文案

#### 修改方案

**1. `types.ts`（L104-113）— AIError.code 枚举扩展**

当前 `AIError.code` 联合类型：
```typescript
// types.ts L107（当前）
public code: 'timeout' | 'rate_limit' | 'service_unavailable' | 'content_filter' | 'invalid_response',
```

新增两个错误码：
- `'content_too_short'`：内容长度不足
- `'offline'`：用户离线

```typescript
// types.ts L107（修改后）
public code: 'timeout' | 'rate_limit' | 'service_unavailable' | 'content_filter' | 'invalid_response' | 'content_too_short' | 'offline',
```

**2. `AIPluginLoader.ts`（98 行）— 新增 `withGuard()` 包装方法**

在 AIPluginLoader 类中新增私有方法 `withGuard()`，统一执行：
- 内容长度前置校验（根据功能类型设定最低字符数）
- 网络在线检查（`navigator.onLine`）

```typescript
private async withGuard<T>(
  fn: () => Promise<T>,
  contentLength?: number,
  minLength?: number,
): Promise<T> {
  // 1. 离线检查
  if (!navigator.onLine) {
    throw new AIError('当前处于离线状态，AI 功能需要网络连接', 'offline', false);
  }
  // 2. 内容长度校验（可选）
  if (minLength != null && contentLength != null && contentLength < minLength) {
    throw new AIError(
      `内容过短（至少 ${minLength} 个字符），请补充更多内容后再试`,
      'content_too_short', false
    );
  }
  // 3. 执行实际 AI 调用
  return fn();
}
```

改造三个公开方法使用 `withGuard()`：

```typescript
async summarizeNote(content: string, options?: SummarizeOptions): Promise<SummarizeResult> {
  return this.withGuard(
    () => (await this.getAIPlugin()).summarizeNote(content, options),
    content?.length, 10
  );
}

async generateFlashcards(content: string, options?: FlashcardOptions): Promise<FlashcardResult> {
  return this.withGuard(
    () => (await this.getAIPlugin()).generateFlashcards(content, options),
    content?.length, 20
  );
}

async evaluateExplanation(concept: string, explanation: string, options?: EvaluateOptions): Promise<EvaluateResult> {
  return this.withGuard(
    () => (await this.getAIPlugin()).evaluateExplanation(concept, explanation, options),
    explanation?.length, 10
  );
}
```

**3. `ElectronAIPlugin.ts`（L33-34）和 `RemoteAIPlugin.ts`（L21-22）— 删除重复校验**

删除两个 Plugin 中 `summarizeNote()` 方法开头的长度校验代码块，校验职责上移至 `AIPluginLoader.withGuard()`。

**4. `useAI.ts`（111 行）— 4 个 hook 的 catch 分支增强**

改造 4 个 hook（`useAISummarize`、`useAIFlashcards`、`useAIEvaluate`、`useAIDuration`）的 catch 块，根据 `error.code` 显示差异化 Toast：

```typescript
catch (error: unknown) {
  if (error instanceof AIError) {
    switch (error.code) {
      case 'content_too_short':
        setState({ data: null, loading: false, error: error.message, isFallback: false });

      case 'offline':

        // 其他错误降级到本地引擎

  }
  // 降级逻辑保持不变
  const fallback = getLocalFallbackMessage('summarize');
  setState({ data: null, loading: false, error: fallback.message + '。' + fallback.suggestion, isFallback: true });
}
```

### T1.4 网络查询 Bug 修复（离线感知 + 错误分类）

#### 现状分析

`apiClient.ts`（75 行）中的 `request()` 函数在发起 `fetch` 前不检查 `navigator.onLine`，导致离线时请求直接超时（30 秒），用户需等待超时才能看到错误提示。

`useAI.ts` 4 个 hook 的 catch 块对网络错误统一降级到 `getLocalFallbackMessage()`，无法区分"离线"和"服务不可用"。

> **与 T1.3 的关系**：T1.3 在 `AIPluginLoader.withGuard()` 中已添加离线检查，本步骤补充 `apiClient.ts` 层面的离线感知，确保非 AI 请求（sync-service 调用）也能快速感知离线。

#### 修改方案

**`apiClient.ts`（75 行）— fetch 前离线检查**

在 `request()` 函数（L13）的 `fetch` 调用前添加离线检查：

```typescript
async function request<T = unknown>(endpoint: string, options: RequestOptions = {}): Promise<T> {
  const { timeout = 30000, headers: customHeaders, ...rest } = options;
  const baseUrl = resolveUrl();

  // 离线快速失败（T1.4 新增）
  if (!navigator.onLine) {
    throw new Error('OFFLINE: 当前处于离线状态');
  }

  // ... 后续逻辑不变
}
```

**`useAI.ts` — catch 分支识别离线错误**（与 T1.3 合并实施）

T1.3 已处理 `AIError.code === 'offline'` 的场景。本步骤补充识别 `apiClient` 抛出的 `'OFFLINE'` 前缀错误：

```typescript
if (error instanceof Error && error.message.startsWith('OFFLINE')) {
  setState({ data: null, loading: false, error: '当前离线，请检查网络连接', isFallback: false });
  return;
}
```

#### 涉及文件

| 文件 | 修改内容 |
|------|---------|
| `client/src/lib/http/apiClient.ts` (L13-14) | `request()` 函数 fetch 前添加 `navigator.onLine` 检查 |
| `client/src/lib/ai/useAI.ts` | catch 分支补充离线错误识别（与 T1.3 合并） |

#### 风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| `navigator.onLine` 在某些 Electron 环境不准确 | 低 | 低 | Electron 主进程可注入网络状态，fallback 仍依赖 fetch 超时 |

### T2.1 ContextMenu 2.0 框架升级

#### 现状分析

当前 `ContextMenu.tsx`（102 行）已实现基础右键菜单功能：
- Portal 渲染到 `document.body`（L65-100）
- 边界检测与位置调整（L24-39）
- 点击外部 + Escape 关闭（L42-63）
- 扁平 `items: ContextMenuItem[]` 接口（L13-17）

局限：
1. **无分组能力**：所有菜单项平铺显示，无法通过分隔线分组
2. **无声明式注册**：每个使用方需手动管理 `onContextMenu` 事件、状态、菜单渲染
3. **接口不兼容扩展**：无法在不破坏现有调用方的前提下添加分组功能

#### 修改方案

**1. 新增分组接口**

```typescript
// ContextMenu.tsx 新增接口
export interface ContextMenuSeparator {
  type: 'separator';
}

export interface ContextMenuGroup {
  label?: string;       // 分组标题（可选）
  items: (ContextMenuItem | ContextMenuSeparator)[];
}

// 扩展 props，保留原 items 向后兼容
export interface ContextMenuProps {
  groups?: ContextMenuGroup[];  // 新接口：分组模式
  items?: ContextMenuItem[];    // 旧接口：扁平模式（向后兼容）
  position: { x: number; y: number };
  onClose: () => void;
}
```

**2. 向后兼容处理**

当 `items` 有值且 `groups` 无值时，内部自动包装为单 group：

```typescript
const resolvedGroups: ContextMenuGroup[] = props.groups ?? 
  (props.items ? [{ items: props.items }] : []);
```

**3. 分组渲染逻辑**

```typescript
{resolvedGroups.map((group, gIdx) => (
  <div key={gIdx}>
    {group.label && (
      <div className="px-3 py-1 text-c1 text-text-tertiary font-medium">
        {group.label}
      </div>
    )}
    {group.items.map((item, iIdx) => {
      if ('type' in item && item.type === 'separator') {
        return <div key={iIdx} className="my-1 border-t border-border/30" />;
      }
      // 渲染 ContextMenuItem（保持原有样式）
      return <MenuItem key={iIdx} item={item as ContextMenuItem} onClose={onClose} />;
    })}
    {gIdx < resolvedGroups.length - 1 && (
      <div className="my-1 border-t border-border/30" />
    )}
  </div>
))}
```

### T2.2 useContextMenu 通用 hook

#### 现状分析

当前各使用右键菜单的页面需手动管理：
- `onContextMenu` 事件绑定
- `position` 状态（`{ x, y }`）
- `isOpen` 状态
- `<ContextMenu>` 组件渲染

这些逻辑在每个使用方重复编写。

#### 修改方案

**新建 `useContextMenu.ts` hook**：

```typescript
// client/src/lib/contextMenu/useContextMenu.ts

import { useState, useCallback } from 'react';

interface ContextMenuState {
  isOpen: boolean;
  position: { x: number; y: number };
  targetElement?: HTMLElement;  // 右键点击的目标元素（供菜单项判断上下文）
}

export function useContextMenu() {
  const [state, setState] = useState<ContextMenuState>({
    isOpen: false,
    position: { x: 0, y: 0 },
  });

  const onContextMenu = useCallback((e: React.MouseEvent<HTMLElement>) => {
    e.preventDefault();
    e.stopPropagation();
    setState({
      isOpen: true,
      position: { x: e.clientX, y: e.clientY },
      targetElement: e.currentTarget,
    });
  }, []);

  const onClose = useCallback(() => {
    setState(prev => ({ ...prev, isOpen: false }));
  }, []);

  return {
    isOpen: state.isOpen,
    position: state.position,
    targetElement: state.targetElement,
    onContextMenu,
    onClose,
  };
}
```

```typescript
interface AuthGuardProps {

export function AuthGuard({ children }: AuthGuardProps) {
  const { session } = useSupabaseSession();  // 复用已有 hook
  const config = getAIConfig();              // 复用已有配置

    config.gatewayUrl.includes('placeholder') ||

}
```

```tsx
function TypewriterText({ text, speed = 30 }: { text: string; speed?: number }) {
  const [displayed, setDisplayed] = useState('');
  const [isComplete, setIsComplete] = useState(false);

  useEffect(() => {
    let index = 0;
    const timer = setInterval(() => {
      if (index < text.length) {
        setDisplayed(text.slice(0, index + 1));
        index++;
      } else {
        setIsComplete(true);
        clearInterval(timer);
      }
    }, speed);
    return () => clearInterval(timer);
  }, [text, speed]);

  return (
    <span>
      {displayed}
      {!isComplete && <span className="animate-blink-cursor">|</span>}
    </span>
  );
}
```

```tsx
// 间隔预览计算
function getIntervalPreview(card: Flashcard, quality: number): string {
  // 模拟 SM-2 算法计算，不修改实际数据
  const { ef, interval, repetitions } = card;
  let newInterval: number;
  let newEF = ef;

  if (quality < 2) {
    newInterval = 1;
  } else if (repetitions === 0) {
    newInterval = 1;
  } else if (repetitions === 1) {
    newInterval = 6;
  } else {
    newInterval = Math.round(interval * ef);
  }

  if (quality === 3) newEF = ef + 0.15;
  else if (quality === 1) newEF = Math.max(1.3, ef - 0.15);

  // 返回人类可读格式
  if (newInterval < 1) return '< 1天';
  if (newInterval === 1) return '1天';
  if (newInterval < 30) return `${newInterval}天`;
  if (newInterval < 365) return `${Math.round(newInterval / 30)}个月`;
  return `${(newInterval / 365).toFixed(1)}年`;
}
```

### T3.7 Electron 托盘常驻（可选）

> **标记为可选**：跨平台兼容性风险高，如时间不足可裁剪

#### 现状分析

当前 Electron 应用关闭窗口后直接退出，用户无法在后台保持应用运行。部分用户希望关闭窗口时最小化到系统托盘，通过托盘菜单恢复窗口。

#### 修改方案

**主进程 Tray 集成**：

```typescript
// electron/main.ts 新增
import { Tray, Menu, nativeImage } from 'electron';

let tray: Tray | null = null;

function createTray() {
  const icon = nativeImage.createFromPath('path/to/tray-icon.png');
  tray = new Tray(icon);
  
  const contextMenu = Menu.buildFromTemplate([
    { label: '打开课伴', click: () => mainWindow?.show() },
    { type: 'separator' },
    { label: '退出', click: () => app.quit() },
  ]);
  
  tray.setToolTip('课伴');
  tray.setContextMenu(contextMenu);
  tray.on('double-click', () => mainWindow?.show());
}
```

**窗口关闭拦截**：

```typescript
// electron/main.ts — 关闭事件拦截
mainWindow.on('close', (event) => {
  if (!isQuitting) {
    event.preventDefault();
    mainWindow.hide();    // 隐藏窗口而非退出
  }
});

// 托盘菜单"退出"时设置标记
let isQuitting = false;
app.on('before-quit', () => { isQuitting = true; });
```

**preload IPC 暴露**：

```typescript

});
```

- 托盘功能仅 Electron 桌面端可用
- PWA 模式下隐藏相关设置项，显示"仅桌面端支持"提示

## 一、测试分层策略

参照 [测试规范与流程](../../phase5/01-测试规范与流程.md) 中的测试金字塔定义，结合 v0.4.0 三个子版本的递进交付特点，定义如下测试分层：

- **L4 UAT 验收**：由产品/用户按 Exit Criteria 检查项逐条手动验证
- **L5 回归测试**：全量自动化用例 + 关键路径手动验证，确保新版本不破坏已有功能

### 1.2 测试原则

## 九、发布渠道与分发方式

参照 [发布流程与回滚预案](../../phase6/01-发布流程与回滚预案.md) 中的分发策略：

### 9.1 Electron 安装包

- **分发渠道**：GitHub Releases
- **产物**：`client/release/课伴_{version}_x64-setup.exe`
- **发布内容**：
  - 安装包文件（.exe）
  - SHA-256 校验和
  - 发布说明链接

### 9.2 PWA

- **分发渠道**：部署 dist/ 到 CDN/服务器
- **更新机制**：Workbox Service Worker 自动缓存新版本，用户刷新页面时检测更新并提示

### 9.3 发布步骤

1. 确认通用 Checklist 和对应子版本专项检查全部通过
2. 同步版本号（package.json、electron-builder.yml）
3. 创建 Git tag：`git tag v0.4.0-alpha.1`（或 alpha.2 / beta.1 / beta.2 / RC）
4. 执行 `npm run build`，部署 dist/ 到 PWA 服务器
5. 执行 `npm run electron:build`，生成 NSIS 安装包
6. 在 GitHub Releases 创建 Release，上传安装包和校验和
7. 编写并发布发布说明

### 9.4 发布节奏

| 子版本 | 时间 | 主题 | 发布类型 | 分发范围 |
|--------|------|------|---------|--------|
| alpha.1 | Week 1-1.5 | 基础体验修复 | 内部测试发布 | 团队成员 |
| alpha.2 | Week 2-4 | 交互增强 | 内部测试发布 | 团队成员 |
| beta.1 | Week 4-8 | 混合方案基础（截图+视觉提取+侧边栏） | 限量用户测试发布 | 团队成员 + 测试用户 |
| beta.2 | Week 8-12 | 混合方案进阶（ASR+AI+智能路由） | 限量用户测试发布 | 团队成员 + 测试用户 |
| RC | Week 12-14 | 动效润色+托盘（可选）+回归测试+发布 | 正式发布 | 所有用户 |

## 十、回滚预案
