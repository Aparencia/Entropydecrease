**陷阱 1 · 行数 —— `Get-Content` 会少算**

**陷阱 2 · 退出码 —— `2>&1 | …` 会把成功的原生命令报成失败**

`cargo`（及任何往 **stderr** 写 warning 的原生命令）在 `2>&1 | …` 或管道下，其 stderr 会被 **PowerShell 5.1 包装成 `NativeCommandError`**，使整个管道以**非零**结束 —— **即使命令本身完全成功**。
实测：`cargo test 2>&1 | Select-Object -Last 40` 报 **exit 1**，而同一次运行的单元测试是 `2337 passed; 0 failed; 6 ignored`、`cargo test --doc` 亦全绿；改用 `2>file` 重定向后 **真实 `exit = 0`**。
⇒ **判定这类命令的结果必须用 `2>file` 重定向，或直接读 `$LASTEXITCODE`，绝不要用 `2>&1 | …`。** 否则会把**绿的门禁误报成失败**（批 0 收尾时差点如此）。
顺带记两条**预存** cargo warning（非批 0 引入）：`lib.rs` 同时属于 `lib` target `app_lib` 与 `integration-test` target `app_lib_tests`（正是它触发了上述假象）；`src/db_task_index_tests.rs:6` 的 `unused import: super::*`。

**陷阱 3 · `cargo test --lib` 的测试二进制在本机启动即崩（2026-09-11 发现，非本系列引入）**

**工具链真相 1 · 本地提交门禁此前从未武装（2026-09-11，批 0-C1 Task 4 发现，已修正）**

**⇒ 本文档此前那句「lint-staged 增加 `{package.json,…}` → `--full` 条目」不要读成「(e) 已在本地全时生效」**：旧接线只在暂存到 `{package.json, scripts/line-limits.mjs, docs/standards/line-limit-exemptions.md}` 三者之一时才跑 `--full`，其余情况只跑**默认模式**（不守 (e)）。实测：只暂存一个改动过的源文件时该段 **0 files / `[SKIPPED]`** ⇒ 同一暂存态下旧门禁 `npx lint-staged` **exit 0**，而新 hook **exit 1** 并报 `(e) 行数不一致：app/src-tauri/src/lib.rs 声明 1025 / 实测 1026`。另一处同类问题是 **glob 假覆盖**：`app/**/*.{ts,tsx,rs}` 命中 **872** 个 tracked 文件，而脚本扫描域只有 **868** 个 ⇒ 差 **4** 个（`app/src-tauri/build.rs`、`app/src-tauri/examples/capture_ocr_diag.rs`、`app/vite.config.ts`、`app/vitest.config.ts`）「命令跑了、文件却没被看见」。**直跑全树消掉的是「命令跑了却看不见」这层假覆盖本身**（glob 不再决定门禁视野），**不是这 4 个文件**：它们仍在 `SCAN_DIRS`（`app/src` + `app/src-tauri/src`）之外、长到 700 行本地仍绿 —— 改直跑后门禁依然看不到它们（扩域须另立批次，见计划「未做（登记）」）。（评审记录为 870 / 差 2 个，那是以 `git ls-files 'app/**/*.ts' …` 数的 —— git pathspec 的 `**` 比 micromatch 少算 `app/*.config.ts` 两个文件；按 lint-staged 实际使用的 micromatch 复核是 872 / 差 4 个。）

**工具链真相 2 · 门禁的失败路径曾是破坏性的（lint-staged@15.5.0，2026-09-11 实测并加固）**

`lint-staged@15.5.0` 默认 `stash:true` + `hidePartiallyStaged:true`，其**失败路径**是「先毁工作树，再赌一次还原」：`git stash create` + `stash store` 备份 → 跑任务 → **失败则 `git reset --hard HEAD`**（清掉整个工作树）→ `git stash apply --quiet --index <备份>` 重建 → `cleanup` 把备份 `stash drop`（实现见 `node_modules/lint-staged/lib/gitWorkflow.js` 与 `runAll.js`）。
⇒ **实测曾使未暂存改动当场消失**：暂存一个故意越线的探针文件、同时在 `docs/standards/README.md` 留一处**纯未暂存**改动，提交 `[FAILED]` 后那处改动**从工作树消失**，且 `git stash list` **为空**（只剩悬空 commit `c85e00a1`）；`git diff HEAD c85e00a1` 证明备份里**确实含**该改动 ⇒ **还原那一半没兑现**。复跑同一实验时内容侥幸还在，但**整个文件被重写**（LF→CRLF、sha256 变化）—— 「内容还在」是那次 `apply` 恰好成功，**不是设计保证**。
⇒ **加固**：`.husky/pre-commit` 改为 `npx lint-staged --no-stash --no-hide-partially-staged`（上游 `--no-stash` 本就 **imply 关掉 hide**；第二个 flag 仍写死，防将来 imply 变化后悄悄退回「藏了未暂存部分却没有备份可还原」—— 那条路失败时必丢）。加固后 lint-staged 在**任何路径**都不碰工作树与索引（不 `stash create`、不 `reset --hard`、不 `checkout --force`、不 `stash drop`），而拦截力不变（实测 `[FAILED]` + `exit=1`、`husky - pre-commit script failed (code 1)`、HEAD 未动、未暂存改动 **sha256 前后相同**）。
**代价（须知）**：① 门禁看到的是**工作树态**，不再是「隐去未暂存部分的索引态」—— 本仓两个检查都是**全树只读扫描**，看工作树反而口径单一，故可接受；② 落在受管 glob 上的**部分暂存文件会在跑完时被整文件 `git add`** ⇒ **不丢内容，但抹掉「只提交一半」的意图**（提交前看 `git status`，`MM` 会变成 `M `）；③ 部分暂存时会残留 `.git/lint-staged_unstaged.patch`（没有步骤再删它）。
**补救（失败后怀疑丢了改动）**：备份是一个 `WIP on <分支>: <HEAD>` 的**悬空 commit** —— `git stash list` 为空**不代表**它不存在：`git fsck --dangling` 列出悬空 commit → `git diff --name-status HEAD <备份ID>` 先确认确实含你的改动 → `git stash apply --index <备份ID>` 整份还原（索引 + 工作树），或 `git checkout <备份ID> -- <path>` 只取回单个文件。
⚠️ **因此切勿运行 `git gc --prune=now`**：这些悬空 commit 是万一丢失改动时的**唯一找回途径**（控制方那次丢失的改动，就是从 `c85e00a1` 找回来的）。
**★ 二轮后（2026-09-11，`31b59239`）：上述整类风险已从路径上消失** —— `.husky/pre-commit` 不再调用 lint-staged（见「工具链真相 1」），故上面写死的 `--no-stash` / `--no-hide-partially-staged` 与本节「代价」的 ②「`MM` 跑完被整文件 `git add`」③「残留 `.git/lint-staged_unstaged.patch`」**都不再适用**（实测：部分暂存文件跑完仍是 `MM`、文件 sha256 前后相同）。本节「补救」一条**仍然有效**（历史悬空 commit 依旧存在，找回方式不变；`git gc --prune=now` 依旧禁止）。
