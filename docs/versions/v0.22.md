### 跨批发现 · 本机工具链的两个「读数陷阱」（工具级，影响全项目）

**陷阱 1 · 行数 —— `Get-Content` 会少算**

本机 harness 的 `pwsh` 实为 **Windows PowerShell 5.1**（ANSI 码页 `gb2312`），`Get-Content` 会按 GBK 解码 UTF-8 文件并**吞掉换行、把行数少算**（实测：`index.ts` 19→12、`paths.test.ts` 130→112、`NoteListView.tsx` 654→609；**全量 868 文件实测最大少算 56 行**：`live_session_pause.rs` 353→297 —— **足以把越 300 红线的文件读成达标**）。
⇒ **AGENTS.md §3 的「≤300 / >600」以 `[System.IO.File]::ReadAllLines(path, UTF8).Count` 为唯一口径**（即 `node scripts/line-limits.mjs`）；禁用 `Get-Content`、`Measure-Object -Line`（只数非空行）与**字节 `0x0A` 计数**（对末尾无换行的文件会少算 1，本仓实测 8 个这样的源文件）。该失真已造成一次真实险情（据此误判 `IconName` 未导出）。
治理侧（口径未定义、15 个 >600 硬限违规、豁免表数值过期）见 [tech-debt/review-2026-09-11.md](../tech-debt/review-2026-09-11.md)；工具侧见批 0-B 台账。

**陷阱 2 · 退出码 —— `2>&1 | …` 会把成功的原生命令报成失败**

`cargo`（及任何往 **stderr** 写 warning 的原生命令）在 `2>&1 | …` 或管道下，其 stderr 会被 **PowerShell 5.1 包装成 `NativeCommandError`**，使整个管道以**非零**结束 —— **即使命令本身完全成功**。
实测：`cargo test 2>&1 | Select-Object -Last 40` 报 **exit 1**，而同一次运行的单元测试是 `2337 passed; 0 failed; 6 ignored`、`cargo test --doc` 亦全绿；改用 `2>file` 重定向后 **真实 `exit = 0`**。
⇒ **判定这类命令的结果必须用 `2>file` 重定向，或直接读 `$LASTEXITCODE`，绝不要用 `2>&1 | …`。** 否则会把**绿的门禁误报成失败**（批 0 收尾时差点如此）。
顺带记两条**预存** cargo warning（非批 0 引入）：`lib.rs` 同时属于 `lib` target `app_lib` 与 `integration-test` target `app_lib_tests`（正是它触发了上述假象）；`src/db_task_index_tests.rs:6` 的 `unused import: super::*`。

**陷阱 3 · `cargo test --lib` 的测试二进制在本机启动即崩（2026-09-11 发现，非本系列引入）**

实测：`cargo test --lib` 报 `error: test failed, to rerun pass --lib`，原因是进程**尚未进入 main** 就以 `0xc0000139`（`STATUS_ENTRYPOINT_NOT_FOUND`）退出——即原生 DLL 加载期失败，与 Rust 代码无关。
本机 DLL 现状（三处同名不同版本）：`C:\Windows\system32\onnxruntime.dll` = **1.17**（2026-09-09 出现）· `ort/onnxruntime-win-x64-gpu_cuda12-1.28.0/lib/onnxruntime.dll` = **1.27.1**（但其 `onnxruntime.lib` 来自 1.28.0，**import lib 与 DLL 版本不一致**）· `ort/onnxruntime-win-x64-1.28.0/lib/onnxruntime.dll` = **1.28.0**。
⇒ **门禁请用 `cargo test --test app_lib_tests`**：同一源码同一时刻该 target 可正常执行——2026-09-11 实测（空载机器）**2357 passed / 0 failed / 6 ignored，exit 0**，覆盖全部 `#[cfg(test)]` 模块（都是 `#[path]` 挂载到 `lib.rs`，与 lib target 同一份测试集）。
   > 注意一项**装载敏感的偶发失败**：`ffmpeg::tests::run_captured_handles_large_output` 内含 10s 墙钟超时，同时跑 `cargo build` + `vitest` 时被拖超时失败，单独重跑 8.55s 通过 ⇒ 判定门禁时须串行执行（或单独复跑该用例再下结论）。
⇒ 治本方向（未执行，留给依赖治理）：把 `ort/` 下的 DLL 与其 import lib 对齐到同一版本，并消除 system32 的同名抢占。本次 DeepSeek 修复的验证全程走 `--test app_lib_tests`，不受该问题影响。
