### 跨批发现 · 本机工具链的读数陷阱与门禁真相（工具级，影响全项目）

**陷阱 1 · 行数 —— `Get-Content` 会少算**

本机 harness 的 `pwsh` 实为 **Windows PowerShell 5.1**（ANSI 码页 `gb2312`），`Get-Content` 会按 GBK 解码 UTF-8 文件并**吞掉换行、把行数少算**（实测：`index.ts` 19→12、`paths.test.ts` 130→112、`NoteListView.tsx` 654→609；**全量 868 文件实测最大少算 56 行**：`live_session_pause.rs` 353→297 —— **足以把越 300 红线的文件读成达标**）。

**文档域可远超此量级（2026-09-11 批 0-C1 补测）**：本批台账（`.superpowers/sdd/2026-09-11-frontend-redesign-batch0c1-line-limits/progress.md`，该目录不进 git）实测 **真实 385 行 / `Get-Content` 报 247 行 —— 少算 138 行（36%）**，因为少算幅度随**中文密度**放大；Task 5 复测同一文件（已增至真实 494 行）时 `Get-Content` 报 356 行，**两次差值同为 138 行** ⇒ 该偏差**不随文件增长而收敛**。⇒ 「禁用 `Get-Content` 数行」**不是只对源码域成立**。
⇒ **AGENTS.md §3 的「≤300 / >600」以 `[System.IO.File]::ReadAllLines(path, UTF8).Count` 为唯一口径**（即 `node scripts/line-limits.mjs`）；禁用 `Get-Content`、`Measure-Object -Line`（只数非空行）与**字节 `0x0A` 计数**（对末尾无换行的文件会少算 1，本仓实测 8 个这样的源文件）。该失真已造成一次真实险情（据此误判 `IconName` 未导出）。

**陷阱 2 · 退出码 —— `2>&1 | …` 会把成功的原生命令报成失败**

`cargo`（及任何往 **stderr** 写 warning 的原生命令）在 `2>&1 | …` 或管道下，其 stderr 会被 **PowerShell 5.1 包装成 `NativeCommandError`**，使整个管道以**非零**结束 —— **即使命令本身完全成功**。
实测：`cargo test 2>&1 | Select-Object -Last 40` 报 **exit 1**，而同一次运行的单元测试是 `2337 passed; 0 failed; 6 ignored`、`cargo test --doc` 亦全绿；改用 `2>file` 重定向后 **真实 `exit = 0`**。
⇒ **判定这类命令的结果必须用 `2>file` 重定向，或直接读 `$LASTEXITCODE`，绝不要用 `2>&1 | …`。** 否则会把**绿的门禁误报成失败**（批 0 收尾时差点如此）。
顺带记两条**预存** cargo warning（非批 0 引入）：`lib.rs` 同时属于 `lib` target `app_lib` 与 `integration-test` target `app_lib_tests`（正是它触发了上述假象）；`src/db_task_index_tests.rs:6` 的 `unused import: super::*`。

**陷阱 3 · `cargo test --lib` 的测试二进制在本机启动即崩（2026-09-11 发现，非本系列引入）**

实测：`cargo test --lib` 报 `error: test failed, to rerun pass --lib`，原因是进程**尚未进入 main** 就以 `0xc0000139`（`STATUS_ENTRYPOINT_NOT_FOUND`）退出——即原生 DLL 加载期失败，与 Rust 代码无关。
本机 DLL 现状（三处同名不同版本）：`C:\Windows\system32\onnxruntime.dll` = **1.17**（2026-09-09 出现）· `ort/onnxruntime-win-x64-gpu_cuda12-1.28.0/lib/onnxruntime.dll` = **1.27.1**（但其 `onnxruntime.lib` 来自 1.28.0，**import lib 与 DLL 版本不一致**）· `ort/onnxruntime-win-x64-1.28.0/lib/onnxruntime.dll` = **1.28.0**。
⇒ **门禁请用 `cargo test --test app_lib_tests`**：同一源码同一时刻该 target 可正常执行——2026-09-11 实测（空载机器）**2357 passed / 0 failed / 6 ignored，exit 0**，覆盖全部 `#[cfg(test)]` 模块（都是 `#[path]` 挂载到 `lib.rs`，与 lib target 同一份测试集）。
   > 注意一项**装载敏感的偶发失败**：`ffmpeg::tests::run_captured_handles_large_output` 内含 10s 墙钟超时，同时跑 `cargo build` + `vitest` 时被拖超时失败，单独重跑 8.55s 通过 ⇒ 判定门禁时须串行执行（或单独复跑该用例再下结论）。
⇒ 治本方向（未执行，留给依赖治理）：把 `ort/` 下的 DLL 与其 import lib 对齐到同一版本，并消除 system32 的同名抢占。本次 DeepSeek 修复的验证全程走 `--test app_lib_tests`，不受该问题影响。

**工具链真相 1 · 本地提交门禁此前从未武装（2026-09-11，批 0-C1 Task 4 发现，已修正）**

本克隆此前**从未安装 husky** —— `core.hooksPath` **为空**、无 `.git/hooks/pre-commit`、无 `node_modules` ⇒ `.husky/pre-commit`（lint-staged）与 `.husky/commit-msg`（commitlint）在本机**对所有提交都是静默失效的**：不只是某个批次，而是**历史上每一次提交**，**包括批 0-A / 0-B / 0-C1 的全部交付提交**（旁证：控制方在本会话提交 40+ 次，从未见过任何 lint-staged / commitlint 输出）。⇒ **新克隆若未 `npm install`，门禁默认失效且无任何提示**（不报错、不警告，提交照常成功）。
现状：**已武装**（`npm install` + `npm run prepare`）—— `node_modules/` 与 `.git/config` 的 `core.hooksPath=.husky/_` 两项环境变更**都不进 git**；此后提交会**真被 lint-staged + commitlint 拦**（已取得实测拦截证据：`(c) 超过 300 行但未登记：app/src/__probe-lines.ts（320 行）`、`husky - pre-commit script failed`、HEAD 未动）。
同一轮还补了**门禁自身的覆盖**：lint-staged 增加 `{package.json,scripts/line-limits.mjs,docs/standards/line-limit-exemptions.md}` → `node scripts/line-limits.mjs --full` 条目 —— 否则「改工具 / 改登记表」在本地没有任何自动拦截（也因此，改 `package.json` 会一并触发这条 `--full` 校验）。

**工具链真相 2 · 门禁的失败路径曾是破坏性的（lint-staged@15.5.0，2026-09-11 实测并加固）**

`lint-staged@15.5.0` 默认 `stash:true` + `hidePartiallyStaged:true`，其**失败路径**是「先毁工作树，再赌一次还原」：`git stash create` + `stash store` 备份 → 跑任务 → **失败则 `git reset --hard HEAD`**（清掉整个工作树）→ `git stash apply --quiet --index <备份>` 重建 → `cleanup` 把备份 `stash drop`（实现见 `node_modules/lint-staged/lib/gitWorkflow.js` 与 `runAll.js`）。
⇒ **实测曾使未暂存改动当场消失**：暂存一个故意越线的探针文件、同时在 `docs/standards/README.md` 留一处**纯未暂存**改动，提交 `[FAILED]` 后那处改动**从工作树消失**，且 `git stash list` **为空**（只剩悬空 commit `c85e00a1`）；`git diff HEAD c85e00a1` 证明备份里**确实含**该改动 ⇒ **还原那一半没兑现**。复跑同一实验时内容侥幸还在，但**整个文件被重写**（LF→CRLF、sha256 变化）—— 「内容还在」是那次 `apply` 恰好成功，**不是设计保证**。
⇒ **加固**：`.husky/pre-commit` 改为 `npx lint-staged --no-stash --no-hide-partially-staged`（上游 `--no-stash` 本就 **imply 关掉 hide**；第二个 flag 仍写死，防将来 imply 变化后悄悄退回「藏了未暂存部分却没有备份可还原」—— 那条路失败时必丢）。加固后 lint-staged 在**任何路径**都不碰工作树与索引（不 `stash create`、不 `reset --hard`、不 `checkout --force`、不 `stash drop`），而拦截力不变（实测 `[FAILED]` + `exit=1`、`husky - pre-commit script failed (code 1)`、HEAD 未动、未暂存改动 **sha256 前后相同**）。
**代价（须知）**：① 门禁看到的是**工作树态**，不再是「隐去未暂存部分的索引态」—— 本仓两个检查都是**全树只读扫描**，看工作树反而口径单一，故可接受；② 落在受管 glob 上的**部分暂存文件会在跑完时被整文件 `git add`** ⇒ **不丢内容，但抹掉「只提交一半」的意图**（提交前看 `git status`，`MM` 会变成 `M `）；③ 部分暂存时会残留 `.git/lint-staged_unstaged.patch`（没有步骤再删它）。
**补救（失败后怀疑丢了改动）**：备份是一个 `WIP on <分支>: <HEAD>` 的**悬空 commit** —— `git stash list` 为空**不代表**它不存在：`git fsck --dangling` 列出悬空 commit → `git diff --name-status HEAD <备份ID>` 先确认确实含你的改动 → `git stash apply --index <备份ID>` 整份还原（索引 + 工作树），或 `git checkout <备份ID> -- <path>` 只取回单个文件。
⚠️ **因此切勿运行 `git gc --prune=now`**：这些悬空 commit 是万一丢失改动时的**唯一找回途径**（控制方那次丢失的改动，就是从 `c85e00a1` 找回来的）。

## 边界（红线延续，全文见规格 §3）

- 不写「自动替你决定」的能力；AI 一律默认关、可降级、须授权
- 不为了动效牺牲可及性：三档强度 + 系统 reduced-motion 优先 + 环境层幅度上限 2%
- 不为「活」而活：每个动效必须能归入四层纲领之一（响应 / 环境 / 编排 / 生长）
