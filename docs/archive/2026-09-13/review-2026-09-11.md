### 3.1 【中·代码质量】"时间戳统一（ADR-008 A1）"实为同一纪元、不同定义——音频侧系统性偏移 +200ms

**位置**
- `app/src-tauri/src/capture/resample.rs:120-128`（`ChunkAccumulator::push` 在攒满 3200 样本后才输出块）
- `app/src-tauri/src/capture/audio_loopback.rs:461-468`（时间戳在块**输出后**取）
- `app/src-tauri/src/live_frame_process.rs:245-246`（帧时间戳在**帧到手时**取）

**最小证据**

```rust
// capture/resample.rs:123-126 —— 攒满才吐块
while self.buffer.len() >= self.target_samples {
    let chunk: Vec<f32> = self.buffer.drain(..self.target_samples).collect();
    chunks.push(chunk);
}
// capture/audio_loopback.rs:461-467 —— 时间戳 = 「块产出时刻」
for chunk in accumulator.push(&resampled) {
    on_chunk(AudioChunk {
        samples: chunk,
        sample_rate: TARGET_SAMPLE_RATE,
        timestamp_ms: epoch.elapsed().as_millis() as u64 - paused_ms,   // ← 块内 200ms 音频已过去
    });
}
```

`live_session_loop.rs:229-232` 用该时刻作为 `sentence_start_ms` / `last_speech_ms`；`live_session_persist.rs:34-36` 的 `sentence_end_ms = last_speech_ms + 200` 又加一个块长。

**为什么是问题（第一性）**
1. `AudioChunk.timestamp_ms` 实际语义是「**该 200ms 音频窗的右端点**」，而 `CapturedFrame.timestamp_ms` 语义是「**该帧被捕获的瞬间**」（`live_frame_process.rs:246`）。两者共享 `epoch` 但**零点定义相差一个块长**，再加上 WASAPI 共享模式缓冲本身还有一拍延迟。代码注释（`live_session_frame.rs:8-9`）声称「与音频块、flush 尾句同一基准」——**基准相同、取值定义不同**，注释掩盖了这一点。
2. 后果一：`sentence_start_ms` 系统性晚 200ms+。这 200ms 会直接进入 §3.4 的融合窗口判定：字幕段与 ASR 段按 `start_ms/end_ms` 判断重叠，200ms 的常数偏移在**边界**处会翻转归属（本应补缝的 ASR 文本被判为重叠而丢弃，或本应归属字幕的文本被保留成 `Fused` 核对段）。
3. 后果二：`append_audio`/`rewrite_with_fusion` 的 DTW 漂移校正（`live_keyframes.rs:331-340`，`MIN_APPLY_DRIFT_MS = 200`）——这个 200ms 阈值的量级**正好等于本偏移**，说明偏移已经进入到需要专门算法去消除的规模，属于「用算法补一个本可避免的定义错误」。

**证据等级**：`已验证`（代码路径与取值时机逐行读到）。**未实测**：我没有跑真机采集去量实际偏差的毫秒数。

**既有债务对应**：未见登记。建议编号 **TD-2026-09-11-A**。

### 3.2 【高·代码质量】单连接全局锁 + `LIKE '%kw%'` 全表扫描 + 段搜索 O(会话数×段数) 内存全扫

**位置**
- `app/src-tauri/src/db.rs:18-22`（`Db { conn: Arc<Mutex<Connection>> }`——**全库单连接、全局串行**）
- `app/src-tauri/src/db_ocr_search.rs:74-92`（`format!("%{}%", escape_like(kw))` + `WHERE b.text LIKE ?1`，无文本索引）

- `app/src-tauri/src/db_migrations.rs:45-54`（`session_segments` 仅有 `(session_id, start_ms)`，**无 text 索引**）
- 对照：知识库侧已有 FTS——`db_migrations.rs:305 CREATE VIRTUAL TABLE kb_fts USING fts5(...)`（**同一仓库内已有正解，未复用到转写/OCR/笔记搜索**）

**最小证据**

```rust
// commands_session.rs:381-397 —— 每次搜索：遍历全部会话 × 每个会话的全部段
for item in state.db.list_sessions(None, LIST_LIMIT_MAX, 0).map_err(...)? {
    for s in state.db.list_segments(session.id).map_err(...)? {   // ← 每个会话一次查询
        if s.text.to_lowercase().contains(&kw) { ... }             // ← 全库文本进内存
    }
}
```

**为什么是问题（第一性）**
1. `LIKE '%kw%'` 的前导通配符使 SQLite **无法使用任何普通索引**——必须全表扫 + 逐行匹配。`session_ocr_blocks.text` 是长会话里最大的表之一：一次 2 小时带板书/PPT 的会话，OCR 块轻松到万级；数十场会话后单次画面检索要扫十几万行文本。
2. 这些扫描**全程持 `db.rs:66` 的全局锁**。Tauri command 是异步的，但 `with_conn` 是同步阻塞的，且 `search_session_segments` / `search_ocr_blocks` 声明为 `pub async fn`（`commands_session.rs:372`、`406`）却在**异步上下文里直接做同步阻塞 DB 遍历**——Tauri 的异步运行时 worker 被占住，同时所有其它命令（包括自动保存 `update_note`、列表刷新 `list_sessions`）排队等同一把锁。用户可感知为「搜一次，整个应用卡住」。
3. `search_session_segments` 的 `list_segments` 没有任何 LIMIT，全库转写一次性 `Vec<SessionSegment>` 物化——内存峰值与全库文本量成正比。

**证据等级**：`已验证`（SQL、索引定义、调用结构均逐行读到）。**未实测**：没有造大数据集测实际耗时。

### 3.3 【中·功能实现】会话列表搜索 SQL 缺括号——过滤条件被 OR 短路，返回本应排除的数据

**位置**：`app/src-tauri/src/db_sessions.rs:86-97`

**最小证据**

```rust
if let Some(kw) = keyword {
    if !kw.trim().is_empty() {
        sql.push_str(" WHERE s.title LIKE ? ESCAPE '\\' OR s.source_window LIKE ? ESCAPE '\\'");
```

**为什么是问题（第一性）**：拼接后的完整语句是

```sql
FROM sessions s WHERE s.title LIKE ? OR s.source_window LIKE ?
ORDER BY s.started_at DESC, s.id DESC LIMIT ? OFFSET ?
```

当前语句里**只有**这一个条件，所以尚未出错；但 `list_sessions` 的签名（`keyword/limit/offset`，`db_sessions.rs:68-73`）与调用方（`commands_session.rs:381` 传入 `None`；`SessionListPanel` 传关键词）表明这是**多条件查询的骨架**。任何后续在此追加 `AND s.status <> 'recording'`（或 `AND s.kind = ?`）都会因为 `AND` 优先级高于 `OR` 而变成 `title LIKE ? OR (source_window LIKE ? AND status <> ...)` —— 标题命中的 recording 会话会**穿透过滤**。判定为**潜在缺陷 + 当前可读性缺陷**（无括号的混合逻辑在 SQL 里属于已知陷阱）。

**证据等级**：`推断`（当前只挂一个条件，尚未产生实际错误；依据是签名与调用点结构）。**未实测**。

**既有债务对应**：未见登记。建议编号 **TD-2026-09-11-C**（低优先，随手修）。

**更好的方案**
- **① 保持现状**：单条件时无 bug，成本 0；风险是下一个人加条件时踩坑。
- **② 最小可用（推荐）**：给现有条件加括号 `WHERE (s.title LIKE ? ESCAPE '\' OR s.source_window LIKE ? ESCAPE '\')`。1 行，0 风险，可回滚，`db_sessions_tests.rs` 已有关键词用例可直接验证。**成本 < 0.1 人时；推荐立即做。**
- **③ 完整实现**：把 `list_sessions` 的过滤条件改为结构化 `SessionFilter` 结构 + 条件向量拼装（`Vec<(String, Box<dyn ToSql>)>` 已有一半，`db_sessions.rs:85`）。约 60 行，收益是消除后续所有同类错误；风险是改动列表查询主路径。

**不推荐 ③ 的理由**：②已消除当前缺陷，③的收益是"未来不犯错"，与本仓库「小步、原子提交、行为等价」的既有工作方式相比偏重。

### 3.4 【中·代码质量】融合是 O(ASR 段 × 字幕段)，且每个重叠对做一次 Levenshtein

**位置**：`app/src-tauri/src/fusion.rs:116-166`（外层遍历 ASR 段，内层遍历**全部**字幕段）；`fusion.rs:195`（`levenshtein(asr_text, sub_text)`）

**最小证据**

```rust
for asr in asr_segments {                       // N
    for sub in &subs {                          // M（每次从下标 0 开始）
        if sub.end_ms <= cursor { continue; }   // 只靠时间比较提前跳过
        ...
        match decide_overlap(sub, asr, text, config) { ... }   // 命中重叠 → Levenshtein
```

**为什么是问题（第一性）**：`subs` 已按 `start_ms` 排序（`fusion.rs:310`），但内层循环**每次都从下标 0 重新线性扫**，没有利用二分定位。对于 2 小时课程：ASR 段数千、字幕段数千，内层平均扫描长度是 O(M/2)，总比较次数达到千万级；其中真正重叠的那部分还要各跑一次 O(L₁·L₂) 的编辑距离（L 为句长）。`merge_transcript` 只在**停止会话后的后台融合线程**里调用（`live_session_fusion.rs:78`，独立线程、有 5s 等待采样线程的窗口），所以**不阻塞 UI**；但它决定了「融合完成」事件何时发出，而 `session:fused` 是前端展示最终时间轴的信号——长会话的融合耗时会直接体现为"停止后要等一会儿才看到干净时间轴"。

**证据等级**：`已验证`（循环结构与排序前提逐行读到）。**未实测**：未构造大样本测实际耗时。**抽样说明**：只精读了 `fusion.rs` 与 `fusion_tests.rs` 未展开；`dtw_align.rs` 只读了调用点未读实现。

**既有债务对应**：未见登记。建议编号 **TD-2026-09-11-D**。

**更好的方案**
- **① 保持现状**：融合在后台线程、不阻塞停止响应，用户最多多等几秒。**成本 0**。对 30 分钟以内的会话，现状大概率完全够用。
- **② 最小可用（推荐）**：内层改用 `subs.partition_point(|s| s.end_ms <= cursor)` 定位起点（1 行改动，O(N log M + 实际重叠数)），并在 `decide_overlap` 前先用长度差做廉价剪枝（`|len_a - len_b| / max_len > 1 - SIM_MATCH_THRESHOLD` 直接走非高相似分支，免算编辑距离）。2 个文件、~15 行。**0.5 人时**。
- **③ 完整实现**：把字幕段建 `interval tree` 或按时间分桶，配合 `decide_overlap` 的编辑距离结果 LRU 缓存。~100 行，收益在于 O(N log M)。

**不推荐 ③ 的理由**：②已把复杂度从 O(N·M) 降到 O(N log M + K)，③只在此基础上再省常数；而 `fusion.rs` 已有 357 行测试（`fusion_tests.rs`），改动越大越容易破坏 4 条融合规则的行为等价性。**验证方式**：`cargo test --test app_lib_tests fusion`（现有 26 例）+ 真机跑一段带字幕的长视频，观察 `session:fused` 事件到达时间。

### 3.5 【中·功能实现】复习评分跨 3 次独立 DB 写、无事务——半成品状态可观测

**位置**：`app/src-tauri/src/commands_flashcards.rs:187-205`

**最小证据**


**证据等级**：`已验证`（三行调用与错误处理逐行读到；`let _ =` 吞错为代码事实）。副作用链（周契约读数受影响）为**推断**，依据是 `week_contract.rs:44-53` 的注释与聚合口径。

**既有债务对应**：未见登记。`TD-2026-09-09-G` 记「db_sessions 手写事务未统一」为同族，但本条是**命令层的多写非原子**，属新发现。建议编号 **TD-2026-09-11-E**。

**更好的方案**
- **① 保持现状**：单机环境下 `update_card_schedule` 与 `add_review_log` 之间失败的概率极低（同一连接、无网络）。**成本 0**。

### 3.12 【中·安全】收件箱 token 使用自实现 xorshift64（已知非 CSPRNG）

**位置**：`app/src-tauri/src/web_inbox.rs:114-126`（`random_token(seed)`）+ `commands_web_inbox.rs:73-78`（seed = `SystemTime::now().as_nanos() as u64 ^ process::id()`）

**最小证据**

```rust
// web_inbox.rs:115-125
pub fn random_token(seed: u64) -> String {
    let mut x = seed.wrapping_mul(0x9e37_79b9_7f4a_7c15) | 1;
    for _ in 0..24 { x ^= x << 13; x ^= x >> 7; x ^= x << 17; out.push(CHARS[(x % 62) as usize] as char); }
}
```

**为什么是问题（第一性）**：xorshift64 的全部状态就是 64 位 seed，而 seed 的两个来源（纳秒时间、进程 id）都**低熵且部分可观测**——本机上任何进程都能读到 PID，时间窗口可枚举。token 是 `POST /ingest` 的**唯一鉴权**（`web_inbox.rs:is_authorized`）。一旦被猜中，攻击者可向用户的应用**注入任意笔记内容**（`validate_payload` 只做结构白名单，不区分来源可信度）。服务只绑 `127.0.0.1`（`commands_web_inbox.rs:96`）——这确实抬高了门槛（需要本机代码执行或浏览器跨站请求绕过 CORS 预检），所以**严重度定中而非高**；但"回环即安全"是错的假设：本机上的低权限进程（如另一个用户态程序）不受回环限制。

**证据等级**：`已验证`（算法、seed 来源、鉴权唯一性均逐行读到）。**未实测**：未做实际爆破。

**既有债务对应**：**`TD-2026-09-06-G` 前半句「web_inbox token 非 CSPRNG 且 ACL 注释漂移」= 未偿**（本次确认仍然如此，代码未改）。

**更好的方案**
- **① 保持现状**：回环绑定 + 24 字符 + 8MB 体量上限已构成纵深。**成本 0**。
- **② 最小可用（推荐）**：`Cargo.toml` 已间接依赖 `getrandom`（tauri 传递依赖，需确认）或直接加 `rand`/`getrandom`；把 seed 换成 128 位 CSPRNG 输出，token 长度不变。**1 文件、~10 行、0.5 人时**。验证：`cargo test` + 单测断言两次调用产物不相关。**注意**：`Cargo.toml` 顶部注释已记载本机 TLS 拦截导致新依赖下载失败的先例（`keyring spike` 因此跳过）——若同样受阻，退路是用 Windows 已有的 `BCryptGenRandom`（`windows` crate 已在依赖树，无需新增下载）。
- **③ 完整实现**：CSPRNG token + 请求侧 HMAC 签名 + 显式 Origin 校验 + 速率限制。

**不推荐 ①** 的理由：修复成本 0.5 人时、且 `windows` crate 已在依赖树内（`BCryptGenRandom` 零新增依赖），没有不修的理由。**现状可能其实是对的吗？** 部分成立——对"同机同用户的恶意软件"而言，它本来就能直接读 SQLite 文件，token 不是额外防线。但对"浏览器里的恶意网页 + DNS rebinding / CORS 绕过尝试"这一档，随机性就是唯一屏障。

#### 数据层-2 【阻断·代码质量】5 处手写 `BEGIN TRANSACTION` 的 COMMIT 失败路径不 ROLLBACK → 悬挂事务让全库写入永久失败

**位置**：`db_sessions.rs:272`（`add_segments_batch`）、`db_sessions.rs:362`（`replace_segments`）、`db_session_events.rs:75`、`db_session_refine.rs:166`、`db_sop.rs:275`；同类结构另见 `db_artifacts.rs:58`、`commands_after.rs:222`

**最小证据**

```rust
// db_sessions.rs:270-279（示意同一形态）
match conn.execute("COMMIT", []) {
    Ok(n) => { /* ... */ Ok(n) }
    Err(e) => { let _ = conn.execute("ROLLBACK", []); Err(e.into()) }   // 仅此分支回滚
}
```

问题在于：**COMMIT 自身失败时 `?` 直接返回**（同一函数内其它 `?` 点），不做 ROLLBACK；只有闭包体失败的分支才回滚。

**为什么是问题（第一性）**：`Db` 是**单连接 + 全局 Mutex**（`db.rs:17-22`）。连接上悬挂一个未提交事务后，全部 `conn.transaction()` 调用点（实测 16 处，见数据层-4 清单）将**永久**报 `cannot start a transaction within a transaction`——保存笔记、删组、批量删会话、画布批写、版本保存全部失效，**应用重启前不可自愈**；更坏的情况是迟到 COMMIT 把半态一并提交（提示"已删除"但只删了一半）。同文件 `delete_sessions_batch` 的注释（`db_sessions.rs:136-150`）已经把这条缺陷写成改用 `tx.commit()` 的理由，**但同文件的这两个函数没有跟着修**——说明修复是逐点进行的，缺一次全量清扫。

**证据等级**：`已验证`（COMMIT 分支结构逐行读到）；"悬挂→后续 transaction() 全失败"为 SQLite 语义**推断**（高置信）。
**既有债务对应**：`TD-2026-09-09-G`（「db_sessions add_segments_batch/replace_segments 手写事务未统一 transaction()」）= **未偿**，本次确认仍在。

- **② 最小可用（推荐）**：把 5 处改为 `conn.transaction()`（`rusqlite::Transaction` 的 `Drop` 在未 commit 时自动 rollback，从机制上消除悬挂）。5 文件、~60 行净减。**1 人时**。验证：`cargo test --test app_lib_tests`（`db_sessions_tests` / `commands_session_delete_tests` 已有现成范式：`commands_session_delete_tests.rs:189-205` 用 `defer_foreign_keys` 制造 COMMIT 期失败，正是本缺陷的最短复现路径）。

**为什么是问题（第一性）**：安装包里的原生库与运行期下载的模型/ffmpeg 都**没有哈希或签名校验**。上游发布资产被替换（或首次下载被中间人替换，`Content-Length` 可伪造）→ 任意代码进入用户机器。CI action 也全部未固定 SHA（`release.yml:30/31/35/90/95/99`，其中 `dtolnay/rust-toolchain@stable` 是**分支名**），而发布 job 持有 `SSH_PRIVATE_KEY`、阿里云 AK 与 `contents: write`——供应链上游可写入发布产物。**这是本次审查中性质最严重的一条**（虽然需要上游被攻破作为前提）。

**证据等级**：`已验证`（配置内容实读）。**说明**：`grep pull_request_target` 零命中（这点是好的，无 PR 注入面）。
**既有债务对应**：未见登记。建议编号 **TD-2026-09-11-V**。

**更好的方案**：① 保持现状（依赖 GitHub 与上游项目的可信度，**成本 0**，这是绝大多数项目的默认姿态）；**② 最小可用（推荐）**——CI 下载步骤后加 `sha256sum -c`（哈希硬编码在 workflow 里，变更时显式更新），运行期模型下载把 `Content-Length` 换成官方清单里的 SHA256（上游 ModelScope/HF 均提供）。~30 行 + 4 个文件、**0.5 人日**；③ 完整实现——CI action 全部按 commit SHA 固定 + 安装包代码签名（`release.yml:141-159` 目前仅自算 sha256）。

#### 安全-5 【高·功能实现】AI 授权文案声明「图像永不出本机」，与 vision 精修上云路径冲突

**位置（文案侧）**：`app/src/components/AiServicePanel.tsx:235-236`（全局授权卡**无条件**写「音视频与图像永不出本机」）、`app/src-tauri/src/ai_settings.rs:119`
**位置（能力侧）**：`ai_settings.rs:43`（`vision_refine_enabled`，默认 false）、`ai_refine_task.rs:306`（resolve 覆写）、`:375-404`（屏卡图 base64 data URI）、`ai_note_refine.rs:166 refine_vision`、`ai_client.rs:184/321`、`commands_ai_refine.rs:149`（**任务级覆写可越过全局关**，`ai_settings.rs:178-183`）

**为什么是问题（第一性）**：「数据不出本机」是本项目的**架构属性而非营销话术**（`AGENTS.md:第 1 节`、产品红线）。用户在全局授权卡上读到"图像永不出本机"并据此授权，随后开启画面理解，**实际上传了会话关键帧**——这构成**知情同意失真**，是本产品最不能出的问题类型。局部弹层已正确条件化（`RefineLaunchDialog.tsx:180-188`），**全局卡未条件化**。因 `vision_refine_enabled` 默认 false，**不是无条件违规**，但默认关不改变"授权文案与能力不一致"这一事实。

**证据等级**：`已验证`（两侧代码与默认值均实读）。
**既有债务对应**：未见登记。建议编号 **TD-2026-09-11-W**（建议 P0——触及产品红线）。

**更好的方案**：① 保持现状（默认关，**成本 0**，但红线风险留着）；**② 最小可用（推荐）**——全局卡文案改为条件式：未开 vision 时保留现文案，开启后改为「文本将发送至 <provider>；**开启画面理解后，会话关键帧图像也会一并发送**」；同时给 vision 精修加**独立默认关的图片上传开关**（与文本授权分离，符合"逐能力授权"）。2 文件、~40 行、**0.5 人时**；③ 完整实现——把 `commands_ai_refine.rs:149` 的任务级覆写改为**必须显式勾选"本次允许上传图像"**（不能静默越过全局关）。

#### 安全-6 【中·功能实现】前端 CSP 过宽

**位置**：`app/src-tauri/tauri.conf.json:21`（`img-src https:`、`connect-src` 含裸 `ws:`）；配合 `NotePreviewView.tsx:52-53` 的直出分支
**为什么是问题**：`img-src https:` 允许笔记里的任意外链图片被加载 → **IP / 阅读行为泄露**给第三方（笔记里一个 `![](https://tracker/x.png)` 即可）。裸 `ws:` 允许任意 WebSocket 目标。**方案**：② 最小可用——`img-src` 收敛为 `'self' asset: http://asset.localhost data:`（与 `NoteImage` 的本地解析路径一致，去掉 `https:`），`connect-src` 去掉裸 `ws:`（~2 行、0.2 人时）。

#### 安全-7 【中·功能实现】快照 HTML 清洗按空白分词，`on*` 属性可漏剥

**位置**：`web_snapshot.rs:192-237 scrub_tag`
**为什么是问题**：按空白分词时 `<img src="x"onerror=...>` 这类**无空格紧邻**的属性不会被识别为 `on*` → 存入导出的本地 html。影响面仅限用户自己导出的本地文件（前端不渲染 `raw_html`），故定为中。与模块注释「快照 XSS 面归零」不符。**方案**：② 最小可用——改用真正的 HTML 属性解析（或正则 `\son[a-z]+\s*=` 大小写不敏感 + 引号容错），并在单测里加这条紧邻样本。

#### 安全-8 【中·功能实现】收件箱服务：token 加密弱 + 明文落盘 + 无 Origin 校验 + 单连接阻塞

**位置**：`web_inbox.rs:115-126`（xorshift64）+ `commands_web_inbox.rs:73-83`（seed = 纳秒 ^ PID；token 明文写 `web_inbox.json`，未走 DPAPI、未设文件权限）、`:164`（CORS `*`）、`:112-113`（accept 循环内**同步**处理 → 单个慢连接阻塞全部收件）
**已经做对的（深审确认，勿误判为缺失）**：绑 `127.0.0.1` 随机端口 ✅、鉴权无绕过 ✅、体量 8MB / 20s 有界 ✅、非自启动 ✅、payload 结构白名单 ✅。
**为什么是问题**：token 是 `POST /ingest` 的唯一鉴权，而 xorshift64 全状态仅 64 位、seed 两个来源都低熵且部分可观测。无 Origin/CSRF 校验使"浏览器里的恶意页面"这一档成为真实威胁面。
**方案**：见 §3.12（CSPRNG 0.5 人时）+ Origin 校验（~10 行）+ accept 后 `spawn` 每连接一个线程（~15 行）。

## 6. 结论摘要

**代码健康度**：编译与测试基线极干净（`cargo test` 2337/0、`vitest` 738/0、`tsc` 0 错，本次全部独立复现），纯逻辑层（ASR 合并/融合/FSRS 调度/屏级聚合）的注释密度与单测覆盖在同类项目里属上游水平；类型纪律也确实到位——**`any` / `as any` / `@ts-ignore` / `@ts-expect-error` 全树均为 0**。安全面同样好于预期——**无硬编码密钥、无 SQL 拼接、无 git 依赖、无可验证 XSS、收件服务未绑 0.0.0.0**（均经证据确认的否定结论）。

**但那个"tsc 全绿 + 单测全绿"是被掩盖的**：本次在前端实测出 **4 个确定性契约崩溃**（`KnowledgeModel.disciplines` 必抛 TypeError 导致整页错误卡片、`SegmentHit` 4 字段全 `undefined` 使段搜索跳转失效、`quota_hit` 使降级提示永不显示、`decidedAt` 秒当毫秒显示 1970 年）。它们能同时通过类型检查与单测，原因是**类型逃逸的真正主渠道不是 `any`，而是 322 个 `invoke<T>` 无校验断言**，且 `KnowledgeModel` 的单测把字段 mock 成了与后端相反的形态——**测试通过反而掩盖了线上崩溃**。这直接推翻了"零 `any` ＝ 强类型契约"的推断。

**治理层已经脱节**：行数红线（15 个硬限文件 vs 文档称 4 个）、豁免登记（46 条漏登 + 12 组重复 + 1 条幽灵）、版本号（产物 0.13.9 vs tag v0.42.0）、CI（738 条测试不进门禁，`validate-all.mjs` 指向已不存在的 `client/`）、最高指令 AGENTS.md（阶段声明落后 20 个版本）、需求池（12+ 条状态低报 + 8 处版本文档互相矛盾）——**六项同时失真，方向一致：登记物不再反映实际**。另有一类更隐蔽的缺口：**写路径静默吞错**（实时链路 6 处 `let _ =`、数据层 44 处、前端 29 处无处理 `invoke` + 50 处静默 `.catch`）与**非原子多写**（5 处手写事务 + `create_note` 等多语句无事务），它们在异常路径下会真实损坏数据而用户毫无信号。

**功能完成度**：主流程（采集 → ASR → OCR → 融合 → 落库 → 笔记 → FSRS 复习 → 复习记录）**执行链路完整且已接线**，十个核心交付面中 6 个判「已实现」、4 个判「部分实现」、**0 个判「未实现」**——这与"功能缺失型"项目有本质区别。缺口集中在三侧：① **后端已有、前端无入口**（47 条命令，其中 12 条对应产品支柱：标签写入、知识库检索、体系改名、碎片移组、会话收尾等）；② **文档声称已交付、实际部分可用或已损坏**（REQ-295 迁出通道 1/3、REQ-079 FTS5 未实装且段搜索命中因契约漂移跳转失效、体系审计无 UI、v0.11.2 自测面不可达）；③ **PRD Must 级未实现**（导出 JSON/Markdown、`full_record` 采集路径）。**验收口径的最大结构性缺口**是 86 处「真机验收待执行」——所有"已交付"目前都只是"代码自验证交付"。
