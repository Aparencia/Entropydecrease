# 课堂采集链路技术审查：要点核查与更佳方案

> **状态**: 前瞻构想（已审查，2026-08-18；本版采纳项见 [ADR-008](../adr/ADR-008-file-import-subtitle-priority.md)）
> **范围**: v0.2.0 实时采集链路（WASAPI 环回 / DXGI+GDI 屏幕 / 流式 ASR / 字幕 OCR / 双源融合 / 生命周期）与 v0.3.0 新增文件导入链路的代码级核查
> **关联**: [头脑风暴：无云端 AI 的内容提取极限](./brainstorming-no-cloud-ai-extraction-limit.md) · [v0.3.0 版本计划](../versions/v0.3.0.md)

## 一、结论摘要

整条采集链路（音频 → 转写 → 屏幕 → 字幕 OCR → 融合 → 会话落库）分层清晰、纯逻辑与系统调用物理分离、防御性编程到位（超时/重连/降级/原子事务全覆盖）。核查发现 **3 个真实缺陷**（时间戳三基准不一致、ASR 句起时间戳近似、引擎池串行阻塞）与 **3 个可即取的质量/性能优化**（头脑风暴 T2 多帧投票、P4 OCR 输入缩小、P3 语音/画面互斥调度简化版），全部在本版（v0.3.0）实施；其余候选（T5 三源交叉验证、P1 采样预算制、V1 视频档案）评估后顺延。

## 二、技术要点核查（四链全景）

### 2.1 音频链（ADR-001/ADR-003/ADR-007）

| 要点 | 实现 | 评价 |
|------|------|------|
| 环回捕获 | WASAPI 共享模式 + LOOPBACK，混音格式兼容 16bit/float + EXTENSIBLE SubFormat 识别 | ✅ 完备（含格式拒绝降级不静默） |
| 输出契约 | 16kHz 单声道 f32，200ms 定长块，与 sherpa-onnx 输入对齐 | ✅ 统一 |
| 静音优化 | RMS < 0.005 判定静音 → 隔块喂入解码（每 2 块喂 1 块），句音频仍全量累积供重打分 | ✅ 静音期 CPU 友好 |
| 端点断句 | 尾静音 2.4s/1.2s 双规则 + 5s 强制断句 | ✅ 课堂节奏调参（原项目验证） |
| 两遍解码 | 端点后 SenseVoice 整句重打分，编辑距离 ≤ 短文本 40% 才替换 | ✅ ADR-003 §5 质量兜底 |
| 自动重连 | 指数退避 0.5s→10s，时间戳基准在重试循环外（重连不重置），恢复事件推送 | ✅ ADR-007 |
| 日志节流 | 仅退避升级时打印 | ✅ 防重连风暴刷屏 |

### 2.2 屏幕链（ADR-002/ADR-005）

| 要点 | 实现 | 评价 |
|------|------|------|
| 双后端 | DXGI 主路径 + GDI 降级 + 周期重建回切 + 窗口矩形每次捕获前刷新 | ✅ ADR-007 自愈 |
| 变化检测 | 8 块 × 60 字节分块采样 hash；字幕区 ≥1 块变化、全帧 ≥2 块（滤鼠标微动）；亚阈值累积防护 | ✅ 生产验证算法 |
| 双速率调度 | 1s tick；字幕区每 2 tick（0.5fps）、全帧每 5 tick（0.2fps）；重叠时字幕优先 | ⚠️ 固定比例，未感知语音活跃度（→ P3） |
| 字幕区裁剪 | 帧底部 1/4 高度，BGRA 内存裁剪 | ⚠️ 全宽送入 OCR，推理成本高（→ P4） |
| 字幕质量 | 3s 时间窗去重（同文本跳过 / 编辑距离 ≤1 合并）+ LCS ≥60% 滚动字幕丢弃 | ⚠️ 去重即丢弃纠错机会（→ T2） |
| OCR 内存化 | BGRA → RgbImage 内存直送，免磁盘临时 BMP（TD-025） | ✅ |

### 2.3 融合链（ADR-005/ADR-006）

| 要点 | 实现 | 评价 |
|------|------|------|
| 融合四规则 | 字幕权威 / ASR 补缝（gap ≥1s）/ 重叠校对（编辑距离 ≤2）/ 空窗丢弃 | ✅ 纯规则本地优先 |
| 落库原子性 | 单事务 DELETE+INSERT（replace_segments），失败回滚不丢原段 | ✅ |
| 停止成本 | 全量重算 + 全表重写，大会话数百 ms~数秒 | ⚠️ REQ-031 本版异步化 |
| 派生视图 | 原始段被覆盖，不可重算/审计/精修 | ⏳ ADR-006（V1.0 派生表） |

### 2.4 生命周期（ADR-007）

关闭保护（CloseRequested 拦截 + 前端确认框）、音频重连（见 2.1）、屏幕自愈（见 2.2）、全局采集徽标——四项机制齐备，已交付待真机验收。

## 三、发现的问题与更佳方案

### A 档：本版（v0.3.0）实施

| # | 问题 | 影响 | 方案 |
|---|------|------|------|
| A1 | **时间戳三基准不一致**：音频块用捕获线程 started、屏幕帧用采样器 started、flush 尾句用会话时钟（session_clock）——ASR 模型加载（1-3s）发生在音频线程启动前，音频时间轴整体滞后于会话起点；flush 尾句反而超前 | 融合 gap 判断、详情页时间轴对齐出现秒级偏移 | **统一会话纪元（epoch）**：run_session 启动即取 `Instant`，注入音频捕获、屏幕 worker、flush 三处，全部 `epoch.elapsed()` |
| A2 | **ASR 句起时间戳近似**：`start_ms = end_ms - 2000` 固定句长 | 融合补缝起止不准；详情页时间轴失真 | 编排层跟踪句首块时间戳（Final 后首个非静音块），真实句起 |
| A3 | **引擎池单线程串行**：ASR（离线转写/重打分）与 OCR 共用一个 worker 线程 | 实时链路中 OCR 阻塞重打分、反之亦然；v0.3.0 文件导入的长转写将整段阻塞实时 OCR | 拆分为 **ASR/OCR 双 worker 线程**（各持单一模型，内存不翻倍，请求并行） |
| A4 | 离线导入（SenseVoice）整段转写只产单段 `[0, duration]`，无句时间轴 | 导入会话详情页只有一大段，无法对齐字幕/画面 | **分窗转写**：WAV 按 30s 窗切分逐窗转写，产真实时间戳段 + 进度事件 |
| B1 | 字幕 OCR 单帧识别错误（同字幕多帧被去重丢弃，无纠错机会） | 字幕是融合的**权威源**，单帧错字全链路污染 | **T2 多帧投票**（头脑风暴）：同字幕多帧字符级多数投票，字幕切换时输出校正文本 |
| B2 | 字幕区全宽（如 1920px）OCR，推理成本随像素近平方增长 | 屏幕 worker 占用 CPU 高 | **P4 OCR 输入缩小**（头脑风暴）：字幕裁剪区缩至 ~960px 宽再送 OCR（字幕文字大，缩小可读性无损） |
| B3 | 固定双速率调度不感知语音活跃度 | 老师静默展示幻灯片/板书时全帧采样仍低频（0.2fps），关键画面漏采 | **P3 简化版**（头脑风暴）：语音活跃时保持字幕区为主；静音期全帧采样提频（每 2 tick），捕捉板书/幻灯片 |

### B 档：顺延（记录在案，不本版实施）

| # | 候选 | 顺延原因 | 去向 |
|---|------|---------|------|
| B4 | T5 冗余信道交叉验证（ASR/字幕OCR/字幕文件三方 RAID 互校） | 需派生视图（ADR-006）保留原始段才有互校对象 | V1.0（与 REQ-032 同批） |
| B5 | P1 采样预算制（QoS：字幕 ≤2fps、全帧 ≤0.5fps 封顶，模块向调度器申请） | 当前固定比例已低于预算上限；形式化调度需整体重构 | v0.4.0 |
| B6 | V1 视频类型档案（VideoProfile 权重/采样策略/产物形态） | v0.3.0 只显式化"字幕/无字幕"二态（M2 即此） | v0.4.0 |
| B7 | P5 有界异步流水线 + 丢帧策略 | **结构上已满足**：屏幕 worker 同步消费（无队列），OCR 耗时超 tick 时天然丢帧；帧比文本廉价原则已成立 | 无需实施（审查结论） |
| B8 | X4 浏览器扩展（B站/YouTube CC 字幕直取） | 交付物形态变重（签名/更新渠道） | 远期 |
| B9 | O1 可信度审计 / O4 离线精修 / O6 双语对照 | 依赖派生视图与多语言管线 | V1.0 |

### C 档：审查确认无需改动

- 引擎不跨线程移动（专用线程独占持有）——规避 FFI Send/Sync 的正确解法，保持
- 实时落库策略（崩溃不丢已识别内容）——保持
- 原子替换（融合失败不丢原段）——保持（REQ-031 异步化后语义不变）
- 静音隔块喂入 + 句音频全量累积——重打分质量与 CPU 的平衡正确，保持

## 五、遗留风险

- A1 统一纪元后，历史会话（v0.2.0 产生）的时间轴偏移不可追溯修正——仅新会话受益（与 ADR-006 迁移策略同口径）
- B3 静音期全帧提频依赖 RMS 判静音准确性；音量低的课程可能误判静音→全帧采样增多（成本可控：变化检测兜底）
- T2 投票延迟落库最多一个去重窗（3s）——崩溃丢失窗口内字幕段的窗口从"实时"变为"≤3s"，可接受（实时落库语义弱化为近实时）
